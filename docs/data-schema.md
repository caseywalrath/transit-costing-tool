# Initial Data Schema

## Purpose

This document defines the TypeScript entity shapes and IndexedDB table boundaries. They are implemented in `src/domain/types.ts` (entities) and `src/persistence/database.ts` (tables and indexes). The code is authoritative where the two differ in syntax; a change to relationships or ownership requires an architectural review and an update to this document.

## Schema conventions

- IDs are UUID strings generated by the application.
- Times and durations are integer seconds.
- Distances are non-negative decimal miles.
- Currency codes use ISO 4217 strings such as `USD`.
- Persisted timestamps use ISO 8601 strings.
- Ordered child records use explicit `sequence` values and stable child IDs.
- Nested arrays are used when children are always loaded and saved with their parent.
- Cross-entity relationships use IDs rather than copied records.
- Derived summaries and current validation results are not persisted as source data.

## Service-day entity

```typescript
interface ServiceDayDefinition extends EntityMetadata {
  id: EntityId;
  scenarioId: EntityId;
  kind: ServiceDayKind;
  name: string;

```

The effective abbreviation is the stored `abbreviation`, or else a default: `WKD`, `SAT`, `SUN`, `HOL` for the standard kinds, and the first three letters or digits of the name, in capitals, for a custom day. Effective abbreviations must be unique within a scenario. The field is not indexed, needs no database migration, and leaves the backup schema at version 10. Scenario copy and import as copy carry it; CSV outputs do not include it.

The four standard service days are created for a new scenario. Annual service days must be a non-negative integer. The application may warn if their sum does not match the analysis-year calendar but must not silently change them.

Pattern validation requires:

- at least two points;
- unique pattern-point IDs;
- contiguous sequence values after normalization;
- existing node references;
- a first cumulative distance of zero;
- non-decreasing cumulative distance;
- repeated node IDs are allowed.

A Pattern whose last cumulative distance is 0 has no distance entered. It is a valid Pattern, but Blocking treats its miles as incomplete and never as 0 miles.

Reverse-pattern creation reverses point order, creates new pattern-point IDs, and reconstructs cumulative miles from reversed segment distances.

Planners enter segment miles; the stored field remains `cumulativeMiles`, so segment entry does not change storage (Decision 0065).

Each runtime band must contain exactly `pattern.points.length - 1` segment values. Runtime assignments must be unique by pattern and service day.

Phase 2R-B adds `RuntimeProfile.calculationRevision`. It starts at zero for a new or copied profile and increments when runtime bands or segment values change; renaming a profile does not increment it. Package 2R-C records the profile ID and revision used for each trip's current scheduled points.

Decision 0032 adds the optional calculation method. Missing values mean `singleBand` for existing backups. Changing the method increments the calculation revision. Decision 0045 requires every profile of a Route to have the same method (a missing value counts as `singleBand`); the field stays on the profile, and the Route's method is the one its profiles share. Dexie version 9 and JSON backup import change a Route whose profiles disagree to the method most of them use (a tie goes to `segmentStart`), raising the calculation revision of each changed profile.

`BlockingBlock` is the normalized shape that every current command reads and writes. The stored `Block` type keeps `blockingScenarioId` and the historical `tripProfileId` optional so that records from before Phase 4 stay readable until the version 4 upgrade or an import normalizes them (placeholder Blocks are discarded). Blocks do not contain a Route ID or duplicate Trip Profile ID. The Block derives its immutable source Trip Profile through its Blocking Scenario. This preserves one ownership authority and permits later interlining. The initial Phase 4 UI filters candidate Trips to one Route and prevents intentional cross-route assignment. Pull-out, pull-in, and deadhead use one timing mode for new and edited records: a non-negative whole-minute offset from their adjacent revenue Trip. Pull-out and pull-in anchor to the first and last revenue Trips; a deadhead anchors to its preceding Trip and must occupy a connection before a successor Trip. Legacy or imported records may retain paired explicit service times. Resolved activity times, layover, compatibility, summaries, validity, and completeness are derived and are not persisted. Revenue hours and Running Time are derived summary measures; Revenue equals Running Time plus usable Layover. The additive nested offset fields are backward compatible and require no database or backup-schema migration.

Blocking Scenario names are unique within a Scenario after trimming and case normalization. Block labels are unique within one Blocking Scenario and service day. A Trip ID may occur once across that complete Blocking Scenario/day but may be assigned differently in another Blocking Scenario.

## Planned frequencies

Decision 0058. A Scenario-owned record, one per Route and Service day, with no link to other Scenarios and no Trip Profile.

| Field | Type | Notes |
| --- | --- | --- |
| `id`, `scenarioId`, `routeId`, `serviceDayId`, `createdAt`, `updatedAt` | | Standard identity and metadata |
| `periods` | `PlannedPeriod[]` | Sorted by `startTime`; never empty (clearing the last period deletes the record) |
| `measureNodeIdByDirectionId` | `Record<EntityId, EntityId>` | Direction to measure node. A missing entry means the default (the first timepoint column's node) |

`PlannedPeriod` is `{ id, startTime, endTime, headwaySeconds }` in service seconds. Start is inclusive and end exclusive; `endTime > startTime`; periods do not overlap; `headwaySeconds` is a whole number from 60 to the period length. The planned times (slots) are `startTime + k × headwaySeconds` below `endTime`. A stored measure node that no Pattern of the direction serves is kept and the default is used (reported as `measureNodeFellBack`). The comparison with built trips is derived and never stored. Plans are written only through `updateScenarioRecords`; duplicating a Scenario or Route, deleting a Route, importing and import-as-copy keep them consistent (Decision 0058 items 10 and 11).

## Costing assumptions

Decision 0027 accepts one Scenario-owned input record shared by all Blocking Scenarios. Cost results and selected Blocking Scenario/year remain derived or workspace state and are not persisted. A Scenario has no record until assumptions are first saved, so upgrading or importing old data never invents a rate or service year. The editor supplies the 3% escalation default.

```typescript
interface CostingAssumptions extends EntityMetadata {
  id: EntityId;
  scenarioId: EntityId;
  currencyCode: "USD";
  /** Absent until a user enters a rate; zero is a real entered value. */
  enteredRate?: number;
  rateYear: number;
  sourceType: "user" | "ntd";
  sourceNote?: string;
  baseServiceYear: number;
  futureYearCount: number; // integer from 0 through 10
  annualEscalation: number; // fraction; default 0.03, must be finite and greater than -1
  /** Decision 0051. The Scenario's shared factors. Written no more since Decision 0062; used by a Trip Profile with no entry below. */
  estimateFactors?: CostingEstimateFactors;
  /** Decision 0062. One entry per Trip Profile of the Scenario at most. An entry, even an empty one, replaces `estimateFactors` for that Profile. */
  tripProfileEstimateFactors?: TripProfileEstimateFactors[];
  /** Decision 0077. At most one entry { tripProfileId, routeId, factors } per Trip Profile × Route. Blank cells inherit the Trip Profile's resolved factors. */
  routeEstimateFactors?: RouteEstimateFactors[];
}
interface CostingFactorPair { layoverFraction?: number; deadheadFraction?: number } // each absent or a fraction from 0 up to but not including 1
interface CostingServiceDayFactors extends CostingFactorPair { serviceDayId: EntityId } // a service day of the same Scenario, at most once
interface CostingEstimateFactors { allDays: CostingFactorPair; serviceDays: CostingServiceDayFactors[] }
interface TripProfileEstimateFactors { tripProfileId: EntityId; factors: CostingEstimateFactors } // a Trip Profile of the same Scenario
```

Factors are saved only by `CostingCommands.saveEstimateFactors(scenarioId, tripProfileId, …)`, which writes that Trip Profile's entry: it drops blank rows and rows of days outside the Scenario, saves all-blank factors as an empty set, and drops entries of Trip Profiles that no longer exist. It never changes `estimateFactors`, and `saveAssumptions` changes neither field. Copying a Trip Profile copies its entry, and deleting a Trip Profile removes its entry, in the same transaction (Decision 0062). Estimated hours, costs, and the implied service check are derived and are not stored. The Dexie schema does not change: both fields are part of the stored `costingAssumptions` record.

Repository and backup validation require one record at most per Scenario, USD currency, a finite nonnegative rate when entered, year values from 1 through 9999, a source year no later than the base service year, and a valid horizon and escalation. Scenario duplication and import as copy assign a fresh assumptions ID and Scenario ID, and map each `estimateFactors` row to the copy's service day. Backup validation of `estimateFactors` (version 7) requires an object with an `allDays` object and a `serviceDays` array, finite fractions from 0 up to but not including 1, and each row's `serviceDayId` a service day of the same Scenario, at most once. Scenario duplication and import as copy also map each `tripProfileEstimateFactors` entry to the copy's Trip Profile and service days. Backup validation of `tripProfileEstimateFactors` (version 11) requires an array whose entries each name a Trip Profile of the same Scenario, at most once, with factors valid as above; a version 1 to 10 file's field is dropped. Scenario deletion removes the record. Blocking Scenario lifecycle does not change it.

## Validation result

Current validation findings are calculated and never stored. Route, Pattern, Blocking, and Costing all report this one shape. Warning acknowledgments are planned but not implemented; the shape has no acknowledgment field. When they are built, they will be persisted separately, keyed by `ruleId` and entity.

```typescript
type ValidationSeverity = "error" | "warning";
type ValidationCategory = "structural" | "operational";

interface ValidationFinding {
  ruleId: string;
  severity: ValidationSeverity;
  category?: ValidationCategory;
  entityType: string;
  entityId: EntityId;
  field?: string;
  messageKey: string;
  parameters?: Record<string, string | number>;
}
```

`category` is set by Blocking (a structural finding rejects a write; an operational finding stays visible). Costing findings omit it. `CostingFinding` is an alias of `ValidationFinding`: its `ruleId` is the former `code`, an assumption finding sets `field`, and the Service day of a Trip or Block finding is the `serviceDayId` parameter.

## Route stops

Decision 0079. A Route-owned record, at most one per Route, stored only while it has at least one stop or one timepoint stop ID (Decision 0080). Stops are passenger stops between timepoints; they are never Nodes or pattern points, and their times are derived, never stored.

```typescript
interface RouteStop { id: EntityId; name: string; stopCode?: string; latitude?: number; longitude?: number; speedLimitMph?: number }
interface StopLocation { latitude?: number; longitude?: number; speedLimitMph?: number }
type StopInterpolation = "equal" | "distance";
type StopTimingRule = "interpolate" | "previous" | "next";
interface PatternStopPlacement { id: EntityId; stopId: EntityId; afterPatternPointId: EntityId; sequence: number; timing: StopTimingRule }
type StopTimeRoundingSeconds = 1 | 30 | 60;

interface RouteStopSet extends EntityMetadata {
  id: EntityId;
  scenarioId: EntityId;
  routeId: EntityId;
  roundingSeconds: StopTimeRoundingSeconds;
  stops: RouteStop[];
  /** Pattern ID → placements, by segment, then sequence. A pattern with no stops has no entry. */
  placementsByPatternId: Record<EntityId, PatternStopPlacement[]>;
  /** Decision 0080. Pattern ID → pattern point ID → that timepoint's stop ID on that pattern. A pattern with none has no entry. */
  timepointStopCodesByPatternId?: Record<EntityId, Record<EntityId, string>>;
  /** Decision 0085. Pattern ID → pattern point ID → that timepoint's location on that pattern. */
  timepointLocationsByPatternId?: Record<EntityId, Record<EntityId, StopLocation>>;
  /** Decision 0086. Absent means "equal". */
  interpolation?: StopInterpolation;
}
```

- A placement sits on the segment from `afterPatternPointId` to the next point by `sequence`; a placement after the last point is not valid. `sequence` orders stops within a segment from 0. One stop appears at most once per segment.
- `stopCode` is optional and unique within the set after trimming, ignoring case. Stop and placement IDs are unique within their set, so Route and Scenario copies keep them.
- Validation (`validateRouteStopSet`): `routeStop.nameRequired`, `routeStop.codeDuplicate`, `routeStop.idDuplicate`, `stopPlacement.stopMissing`, `stopPlacement.idDuplicate`, `stopPlacement.repeatedInSegment`, and `routeStopSet.roundingInvalid` are errors; `stopPlacement.timingOutOfOrder` is a warning.
- A timepoint stop ID (Decision 0080) is trimmed and non-blank, and names a point of its own pattern. It is not unique: patterns of one direction share it through Fill and Copy. A pattern edit keeps it only while its point remains and stands on the same Node (`reconcileTimepointStopCodes`).
- Locations (Decision 0085): latitude and longitude are given together or not at all, latitude from −90 to 90, longitude from −180 to 180, speed limit above 0; a timepoint location follows the same lifetime as a timepoint stop ID and is filled or copied between patterns of the same direction. Distance spacing (Decision 0086) uses great-circle miles along opening timepoint, stops, closing timepoint; a segment missing a location, or of length 0, is equally spaced.
- Every Scenario write prunes placements and timepoint stop IDs whose pattern or point no longer exists, stops no placement uses, and sets left with neither stops nor timepoint stop IDs (`pruneRouteStopSets`). Writes go through `updateScenarioRecords` (`saveRouteStops`, stop copy and undo) or the Route edit commit (placement reconciliation).

```typescript
  getScenarioRecords(scenarioId: EntityId): Promise<ScenarioRecords | undefined>;
  saveScenarioRecords(records: ScenarioRecords): Promise<void>;
  commitRouteEdit(records: ScenarioRecords): Promise<void>;
  getRouteDefinition(routeId: EntityId): Promise<RouteDefinitionAggregate | undefined>;
  saveRouteDefinition(aggregate: RouteDefinitionAggregate): Promise<void>;
  listDirections(routeId: EntityId): Promise<RouteDirection[]>;
  getProjectSnapshot(projectId: EntityId): Promise<ProjectSnapshot | undefined>;
  saveProjectSnapshot(snapshot: ProjectSnapshot): Promise<void>;
}
```

Exact interfaces should follow use cases. Do not create a generic repository abstraction that hides required transaction boundaries.

The Costing input port is separate from schedule queries:

```typescript
interface CostingAssumptionsRepository {
  getCostingAssumptions(scenarioId: EntityId): Promise<CostingAssumptions | undefined>;
  saveCostingAssumptions(value: CostingAssumptions): Promise<void>;
}
```

Saving validates the record and Scenario ownership. Scenario and project snapshot writes include the assumption record in their existing transaction so copy, replace, and deletion stay consistent.

The authoritative trip repository exposes trip, block, pattern, assignment, and runtime-profile queries plus atomic `insertTripsAtomically` and `saveTripChangesAtomically` operations. Package 3A adds optional structural repository commands `commitRuntimeCopyAtomically` and `replaceTripsForDayAtomically`; both validate the complete affected graph before writing and execute one transaction. Runtime-copy and Trip-copy previews carry source signatures that the application recalculates immediately before commit. The historical generation-set repository methods remain only so that the `generationSets` table and old backups (including version 3 files) can still be read and restored (review decision 13). The pre-2R generation-set screens that called them were removed in review package X01, and the revised commands do not use them.

## Transactions

Use one transaction for operations that must remain consistent, including:

- creating a scenario and its standard service days;
- cloning a scenario and all owned records;
- deleting a scenario;
- saving a route with node and pattern changes that affect references;
- committing a reviewed Node or Pattern edit with reconciled directions, runtimes, trips, and affected blocks;
- regenerating a trip set and updating affected block references;
- creating or duplicating a Blocking Scenario with its complete all-day Block graph;
- deleting a Blocking Scenario and all owned Blocks;
- assigning or atomically reassigning a Trip when one or two Blocks are affected;
- importing a complete project backup.

## Database versions and migrations

The first implementation starts at database version 1. Version 2 adds a non-unique `runtimeProfileId` index to `runtimeAssignments` for profile lifecycle queries. Phase 2TP increments the database to version 3 with a `tripProfiles` store and Trip-profile ownership indexes on Trips and Blocks. Package 4B increments the database to version 4 with `blockingScenarios` and Blocking-Scenario ownership indexes on Blocks. The version 4 migration discards pre-Phase-4 placeholder Blocks while preserving Trips, Trip Profiles, and all other scheduling records. Version 5 adds the Scenario-owned `costingAssumptions` store and leaves it empty for existing Scenarios; records are created lazily when Costing inputs are saved. The preliminary `costPlans` store remains untouched and unused so the upgrade does not discard legacy data. Version 6 adds the one-step `tripRegenerationUndo` store. Version 7 changes no store. Its upgrade function repairs Scenarios that were duplicated before duplication remapped Node references (Decision 0038): in each Scenario that records a `sourceScenarioId`, the `fromNodeId` and `toNodeId` of pull-out, deadhead, and pull-in activities that name a Node of another Scenario are repointed to the copy's own Node (same Route name; same Node name, using the position in the Route's Node order when a name repeats). Where a Scenario in the copy's `sourceScenarioId` chain no longer exists, pull-out To, pull-in From, and deadhead From and To are taken from the adjacent Trip endpoints, and a pull-out From or pull-in To that cannot be inferred is cleared. The upgrade writes only Blocks that changed and no other record. Version 8 adds the compound index `[scenarioId+tripProfileId]` to `trips` (every earlier index stays) and deletes every Block whose `blockingScenarioId` is absent, null, or empty: the placeholder Blocks that imports of version 3 and 4 backup files stored before package P04. It writes nothing else; if the clean-up throws, it logs a warning and leaves the data as it was, so the database still opens. Version 9 changes no store. Its upgrade gives every Runtime profile of a Route the method most of the Route's profiles use (Decision 0045), writing only the profiles whose method changes, each with the next calculation revision; Trip times are not rewritten, and a failure leaves the data as it was. Version 10 adds the `plannedFrequencies` store (`id, scenarioId, routeId, [routeId+serviceDayId]`) with no data upgrade; existing Scenarios have no plans. Version 11 adds the `routeStopSets` store (`id, scenarioId, routeId`) with no data upgrade; existing Routes have no stops. Version 12 changes no store and moves `Node.stopCode` into the stop sets (Decision 0080). Version 13 adds the `restorePoints` store (`id, projectId, createdAt`) and the `restorePointPayloads` store (`id`) with no data upgrade; both start empty (Decision 0081). Version 14 changes no store: its upgrade gives each Trip that is current by the revision rule the `runtimeInputsSignature` of its source profile and writes only those Trips; a failure leaves the data as it was (Decision 0081 item 11). Version 15 deletes the `tripRegenerationUndo` store (Decision 0081 item 12); no other data changes.

Trip staleness (FX7): `provenance.calculationSource.runtimeInputsSignature` is a fingerprint (`runtimeInputsSignature` in `src/domain/runtime.ts`) of the profile's method and, in band order, each band's start, end, and segment runtimes; band ids, labels, and the profile name are not inputs. A Trip with a signature is stale when the assigned profile's current signature differs, so an edit that is reverted leaves its Trips current. A Trip without one keeps the revision rule. The trip CSV is unchanged.

Restore points: a `RestorePointSummary` holds `id`, `kind` (the command, or `restore` for a recorded restore, with `restoredKind`), `scope` (`scenario` or `project`), `projectId`, the optional `scenarioId`, `createdAt`, `names` (the context names, read from the records before the command), `counts` (removed, changed, and added rows per collection), the optional `quantity` and `detail` used by the label, and `sizeEstimate` (the payload's JSON length at capture). The matching `RestorePointPayload` holds either `change` (the removed rows, the previous versions of changed rows, the added ids, and a stamp of each changed or added row, per collection of `ScenarioRecords`) or `projectSnapshot`. The summary and its payload are written in the transaction of the command. Retention (`RESTORE_POINT_POLICY` in `src/domain/restorePoints.ts`): the newest 20, none older than 30 days, at most 50 MB of `sizeEstimate` in total; the oldest go first and the newest is always kept; a storage-full failure keeps the newest 5. Trip changes (`regenerateTrips`, `changeTripStartTime`, `changeTripPattern`, `shiftTrips`, and recorded restores of them) are a separate group under `TRIP_CHANGE_POLICY`: the newest 10, none older than 30 days. A summary may carry `refs` (the Route, Service day, Trip profile, and other ids the command ran in); the Trips menu uses them to offer the trip change in view. The tables are not exported in JSON backups, not copied with a Scenario or Project, not deleted with their project, and not cleared by backup restore.

Each later schema change must:

1. increment the database version;
2. define an explicit migration;
3. preserve existing user data or fail without partial writes;
4. include a migration test;
5. update this document when entity meaning or ownership changes.

Database version and export-schema version are related but distinct: the export-schema version (8) is written into every JSON export by `exportProjectJson`, and no code stores it in `appMetadata`. The optional `applicationVersion` field of an export is accepted on import but no caller supplies it yet.

## Backup schema

A JSON backup contains:

- format identifier;
- export-schema version;
- export timestamp;
- application version when available;
- one complete project graph: the project, scenarios, service days, routes, nodes, directions, patterns, pattern points, runtimes, Trip profiles, trips, Blocking scenarios, and blocks.

The implemented export schema is version 11 and stores directions, runtime profiles, assignments, Trip profiles, Blocking Scenarios, optional Costing assumptions (with their optional estimate factors, Decision 0051), trips, and Blocks as top-level arrays. Version 7 differs from version 6 only by the optional `estimateFactors`. Version 9 differs from version 8 only by the optional `maxVehicles` rule inside the `autoBlocking` record (Decision 0056; when present it must be a whole number of at least 1, otherwise import fails with `autoBlocking.limitVehicles at maxVehicles`). Version 8 differs from version 7 only by the optional `autoBlocking` record on a Blocking Scenario (Decision 0055); import validates its shape and runs `validateAutoBlockingRules` against the Scenario's Patterns, Nodes and Service Days, failing with `Invalid project backup: blockingScenarios[i].autoBlocking <problem>`. A version 1 through 7 file never holds the field; one found there is dropped without failing. Import-as-copy remaps the Pattern, Route, Node, Service Day and Blocking Scenario identifiers inside the record, drops rows whose reference has no mapping, and sets `builtAt` to the import time. The IndexedDB stores and indexes are unchanged (no database version bump). Versions 1 through 7 remain readable; versions 1 through 4 predate normalized Blocking Scenarios and retain their existing import normalization. Version 5 imports with no Costing assumptions. The schema 6 and 7 parsers validate assumptions and their Scenario ownership before any repository write. Historical service-day totals above 365 remain intact and make Costing calculations invalid until corrected. Empty authoritative exports omit the historical `generationSets` property; populated historical records remain readable for transition purposes. Version 1 through version 3 imports are normalized to one Default Trip profile per Scenario. Current normalized Blocks reference only their Blocking Scenario; Trip Profile ownership is derived through that relationship.

Costing CSV reporting produces one ZIP containing `costing-assumptions.csv`, `costing-results.csv`, and `costing-exclusions.csv`, for a blocked basis (a Blocking Scenario) or an estimated basis (a Trip Profile, Decision 0051). Each file has a `costBasisKind` column (`blocked` or `estimated`) after `tripProfileName` (exclusions excepted); an estimated basis leaves the Blocking Scenario columns blank. Assumptions add `allDaysLayoverFraction` and `allDaysDeadheadFraction`. Result rows cover each service day and service year plus independently calculated annual totals, and add trip count, trips without a run time, running hours, and the layover and deadhead factors with their source (`serviceDay` or `allDays`); blocked rows leave these blank and estimated rows leave the Block counts blank. USD values use two decimals, hour quantities use four decimals, applied USD/VRH rates use four decimals, and factors use six decimals. Exclusion rows identify affected Blocks and reason codes and report unassigned Trip counts by service day; an estimated basis reports `tripsWithoutRunTime` rows instead. CSV does not restore project data.

Import must validate the complete payload before opening a write transaction. ID collision policy must be explicit: replace an existing project only after confirmation, or import with remapped IDs as a new project.

Version 10 adds the optional top-level `plannedFrequencies` array (Decision 0058); the key is omitted when a project has no plans, so such a file differs from version 9 only by its version number. Versions 1 to 9 stay readable and import with no plans.

Version 18 (current, Decision 0090 item 16) adds the optional `gtfsExportSettings` on a Scenario: `startDate` and `endDate` (`YYYY-MM-DD`; the end is not before the start), `holidays` (each a `date` inside that range and a `serviceDayId` of the Scenario), `mapLines` (`straight` or `none`), and the optional text fields `agencyName`, `agencyUrl` and `agencyTimezone`. Import checks each field that is present and names it in its message (for example `Invalid project backup: scenarios[0].gtfsExportSettings.holidays[0].date must fall inside the export range`). Dates are checked against the calendar, so `2026-02-30` is refused. Import as copy and Scenario duplication carry each holiday to the copy's service day and drop a holiday whose day has no copy. Deleting a service day removes its holidays (`removeServiceDayFromFeedFields`). A blank agency name, URL or time zone is accepted by the backup; the GTFS export refuses it (Decision 0090 item 19). Versions 1 to 17 stay readable and import with none of the settings. The Dexie schema stays at version 15: no store or index changes.

Version 17 (Decision 0089 items 38 to 42) adds the optional `importNotes` array on a Scenario, the optional `gtfsRouteId`, `gtfsRouteType`, `color` and `ownAnnualServiceDays` on a Route, and accepts `provenance.creationMethod` `"feed"` on a Trip. Import checks each field that is present and names the field in its message (for example `Invalid project backup: routes[3].color must be six upper-case hexadecimal digits`). A Route's own counts must name only service days of its Scenario, be whole numbers of 0 or more, and total at most 365. An import note's dates must name only service days of its Scenario and read `YYYY-MM-DD`. Import as copy and Scenario duplication remap the service-day keys of both; Route duplication copies them unchanged. Deleting a service day removes its key from the Routes and import notes of its Scenario (`removeServiceDayFromFeedFields` in `src/domain/project.ts`); no screen deletes a service day yet (backlog: custom service day delete). Versions 1 to 16 stay readable and import with none of the new fields. The Dexie schema stays at version 15: no store or index changes.

Version 16 (Decisions 0085 and 0086) adds the optional stop `latitude`, `longitude` and `speedLimitMph`, the optional `timepointLocationsByPatternId` and `interpolation` on each stop set, and accepts `roundingSeconds` 1. Import refuses a malformed location (an incomplete pair, a value out of range, or a location on a point not of its pattern). Versions 1 to 15 stay readable and import with no locations and equal spacing. The Dexie schema stays at version 15.

Version 14 (Decision 0080) adds the optional `timepointStopCodesByPatternId` to each stop set and no longer writes `Node.stopCode`. Import checks that each value is a non-blank string of a point of its pattern. A version 13 file's `Node.stopCode` is moved onto every point of its Route's patterns that stands on that Node (a point that already has a stop ID keeps it), and a Route without a stop set gets one.

Version 15 adds the optional `runtimeInputsSignature` to a Trip's `provenance.calculationSource` (Decision 0081 item 11, FX7); when present it must be a non-empty string, and a file that breaks this fails with `Invalid project backup: trips[N] has an invalid runtime inputs signature`. Versions 1 to 14 stay readable. On import of any version, a Trip that records a source without a signature and is current by the revision rule against its source profile gets that profile's signature (`withRecordedRuntimeSignatures`), as the Dexie version 14 upgrade does.

Version 13 adds the optional top-level `routeStopSets` array (Decision 0079; omitted when no Route has stops) and the optional `Node.stopCode`. Import validates each set's shape (string IDs, `roundingSeconds` of 30 or 60, stops with an `id` and `name`, placements with string IDs, a whole `sequence` of 0 or more, and a known `timing`), its metadata, its owners, and `validateRouteStopSet`, and fails with `Invalid project backup: <message>`; a `stopCode` must be a non-empty string. Sets are pruned against the imported Routes and Patterns. Import as copy remaps the set, Route, Scenario, Pattern keys and `afterPatternPointId`, and keeps stop and placement IDs. Versions 1 to 12 stay readable and import with no stops; every check that applied to version 12 applies to version 13.

Version 12 differs from version 11 only by the optional `routeEstimateFactors` array inside a Costing assumptions record (Decision 0077). Its validation requires an array whose entries each name a Trip Profile and a Route of the same Scenario, each pair at most once, with factors valid as for `estimateFactors`; a version 1 to 11 file's field is dropped. Scenario duplication and import as copy remap the Trip Profile, Route and service-day IDs. `CostingCommands.saveRouteEstimateFactors` writes one pair's entry and removes it when the factors are all blank; Route deletion removes a Route's entries in the same write, and Route duplication copies them.

Version 11 differs from version 10 only by the optional `tripProfileEstimateFactors` array inside a Costing assumptions record (Decision 0062). Versions 1 to 10 stay readable; the field found in one of them is dropped without failing the import. Import validation rejects a plan whose Route, Service day, direction or node is missing, or whose periods break the rules above. Import-as-copy remaps the plan, Route, Service day, period, direction and node identifiers.

### Import rules

Parsing a backup returns the project graph and an import report (`BackupImportReport`: `recoveredNodeReferences`, `recoveryFindings`, `discardedPlaceholderBlocks`). Parsing and validation finish before any repository write, and every rejection carries a plain-language message. Those from the checks on the file's own fields, Trips, Blocks, and activities begin "Invalid project backup:" and name the problem; a few older checks (runtime assignments, the supported format and version) word theirs differently. A field of an unexpected type that no check names is reported as "the file contains data in an unexpected form", never as a raw runtime error. Files of export-schema versions 1 through 6 import.

- **Placeholder Blocks.** A Block whose `blockingScenarioId` is absent, null, or empty is a pre-Phase-4 placeholder (a present but malformed value rejects the file). It is discarded on import and counted in `discardedPlaceholderBlocks` (Decision 0019 item 13). Version 3 and 4 files hold only such Blocks; a placeholder in a later file is discarded the same way.
- **Block ownership.** A normalized Block stores no `tripProfileId`; its Trip Profile follows from its Blocking Scenario. Import adds none. A stamped `tripProfileId` in an older export is dropped when it equals the Blocking Scenario's Trip Profile and rejects the file when it differs. `export(import(file))` leaves Blocks as they were.
- **Scenario copies.** Pull-out, deadhead, and pull-in Node references of Scenario copies made by the older code are repaired before the checks below (Decision 0038). A reference that recovery could not repair is reported in `recoveryFindings` and does not reject the file.
- **Trips** must have a `provenance` object; a Route, Pattern, and service day of their own Scenario (the Pattern on the Trip's Route); stop times that visit each Pattern point once, with whole, non-negative times; and a known Trip Profile of their Scenario.
- **Blocks** must belong to a Blocking Scenario of their Scenario and to a service day of that Scenario; carry a label that is unique within the Blocking Scenario and service day (trimmed); and contain activities with a unique `id`, a supported `type`, a whole `sequence`, numeric time, offset, and mile fields, and Node references that belong to the Block's Scenario.
- **Block rules.** Each Block passes the structural Blocking rules of `validateBlockingBlock` (one pull-out first, one pull-in last, a deadhead only between two Trips and only one per connection, valid times, offsets and miles, Trips from the Block's own Scenario, service day, and Trip Profile), and each Trip appears once in its Blocking Scenario. Gaps in activity `sequence` numbers are tolerated and renumbered by the next edit.
- **Generation sets** (historical) must carry a `limit` object.
- **Accepted by design:** unknown extra fields (kept), Direction columns whose Node is missing but recoverable from Pattern points, and service-day totals above 365 (Costing reports them).


## CSV exports

Phase 1 should export:

- routes;
- nodes;
- patterns;
- pattern points.

Phase 2R adds runtime bands, directions, direction columns, authoritative trips, scheduled points, placeholder blocks, and block activities. Phase 2TP adds `tripProfileId` and `tripProfileName` to the Trip and placeholder Block CSV outputs. Phase 4 replaces Blocking exports with Blocking Scenario, Block, block-activity, and derived block-summary files scoped to one Blocking Scenario. Summary files include validity and completeness fields. The authoritative Trip CSV contains creation method and runtime calculation source fields and does not include generation-set columns. A legacy export method (`RouteDefinitionService.exportCsv`, which still includes a generation-sets file) remains but no screen calls it; the Route CSV export uses `exportAuthoritativeCsv`. CSV files are reporting and exchange outputs, not full backups.

The Trips **Export trips with stops CSV** (Decision 0079, `stopTimesCsv`) writes the displayed schedule in long form, one row per Trip per timepoint or stop in pattern order: `Trip, Direction, Pattern, Stop Order, Stop ID, Stop Name, Timepoint, Time, Block`. `Trip` and `Stop Order` are 1-based positions, `Timepoint` is `Yes` or `No`, and `Time` is the Trip's saved time at a timepoint or the derived stop time (empty when a segment has no usable times). Free-text columns are protected against spreadsheet formulas.
