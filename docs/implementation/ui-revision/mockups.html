Section 2

Three surface levels

Every panel today has the same white card and heavy teal top border, so nothing stands out. The proposal gives each kind of content its own visual weight. The tab mockups in sections 3 to 6 apply these rules.

Level 1

Work surface

What you edit or read most on the tab: the Trips table, the Pattern editor, Current block, Cost breakdown. White panel, thin border, 16 px bold title, panel actions in its header.

Level 2

Supporting panel

Context and summaries: Service days, Weekday summary, Exclusions, Yearly outlook. No card border; a muted 14 px title over a lightly tinted box. Visually recedes.

Level 3

Inline note

One-line status and guidance, such as "No current issues" or "Enter all non-revenue miles…". Text with a small icon, no box. Colour is used only for warnings and confirmations.

The teal accent is reserved for three things: the active tab, primary buttons, and the selected item. Thick borders are dropped everywhere.

Section 7 · interactive

Save pattern and spreadsheet cells

This is a working model of the Runtimes table with spreadsheet-style cells, together with the Service day counts that save automatically. Edit a few cells, then use Discard or Save. The status in the bar at the top follows what you do.

The rule

A single field that stands alone (a name, a service-day count, a selector) saves when you leave it and shows a brief "Saved". A table or form whose edits must be reviewed or saved together (Nodes, Pattern, Runtimes, Costing assumptions) collects edits and shows the save bar at the bottom of that panel.

What stays the same

The impact reviews (for example, saving a Pattern that changes trips) still open after you press Save. Leaving a tab with unsaved edits still asks first. Only the placement and look are being unified.

Keys

↑ ↓ ← → move · type to replace · Enter or F2 edit · Enter commit and move down · Tab commit and move right · Esc cancel. Run times accept :05, :05:30, 5, or 5.5.

Section 8 · explanation

What design tokens are, and why they help here

A design token is a named value for one visual decision, such as "the colour of a warning" or "the space between form fields". The stylesheet then refers to the name instead of repeating the raw value. It is the same idea as a named cell in a spreadsheet: change the value in one place and every formula that uses it updates.

Today

168 colours, 21 font sizes, 7 corner radii

Counted in src/styles.css. Many are near-duplicates (for example, five slightly different blue-greys for label text). Each was picked separately when a panel was built, which is why panels look subtly different from each other.

Proposed

About 22 colours, 6 sizes, 2 radii

Each named by its role, not its appearance: --color-text-muted, not --grey-3. A rule like "warnings are amber" is then enforced simply by everyone using the same name.

Cost

Mostly mechanical

Once you approve the values, replacing raw colours with token names is a find-and-map exercise with screenshot comparison, which suits a structural (Luna) package. It changes no behaviour.

Example

/* Today: the same idea written three different ways */
.primary        { background: #1b668d; }
.tab.active     { background: #24485d; }
.menu-check     { color: #1b668d; }
.trip-status    { color: #6b4d1c; }   /* warning text */
.recalc-fallback{ color: #835521; }   /* also warning text, different brown */

/* With tokens: one definition per role */
:root {
  --color-action:     #1b668d;
  --color-warn-text:  #7f520f;
}
.primary, .tab.active { background: var(--color-action); }
.menu-check           { color: var(--color-action); }
.trip-status,
.recalc-fallback      { color: var(--color-warn-text); }

Proposed colour roles

These are the exact values used in the mockups on this page.

  • Spacing: 4, 8, 12, 16, 24 px. Radius: 5 px for controls, 7 px for panels. Type: the six sizes in section 9.
  • Dark mode becomes a matter of supplying a second set of values for the same names. It is not proposed now; tokens keep that door open at no extra cost.

Section 9

Typography: Source Sans 3

Source Sans 3 is an open-source typeface from Adobe. It is narrower than Inter, which helps dense tables, and it has true fixed-width ("tabular") digits. The font files would be bundled with the app, so every computer shows the same font and no network request is made.

Section 12

Recorded and deferred

These items would be written into the UI/UX implementation plan as deferred, so they are not lost:

  • Command palette (Ctrl/⌘ K) and keyboard shortcuts.
  • Glossary tooltips next to domain terms.
  • Team readiness: first-run screen with a sample project, in-app help, a "What's new" note, a clearer flow for sharing a project copy, and a settings page.
  • Accessibility beyond quick wins. The quick wins included in this revision: a visible focus outline on every control, label contrast that meets WCAG AA (the token palette above does), larger icon targets, and block numbers shown as text beside the colour.
  • Dropped: workflow-step tabs, left sidebar, density toggle.
