# UI Conventions

## Phase 3R acceptance

The Runtime and Trip header-action conventions below are implemented and accepted through Phase 3R. They retain separate Runtime and Trip scopes, preserve the existing shared workflow-section system, and do not establish a convention for top-level Scenario/Data menus or Route-tab Node/Pattern menus.

## Application header (UR-5, Decision 0047)

- The header has two rows. Row 1 (`app-bar`) holds the application name, the primary tabs (`aria-current="page"` on the active one), and one status line. Row 2 (`scope-bar`, region "Scope") holds the Project and Scenario switchers, a divider, the active tab's scope selectors, and the tab's "⋯" menu. Row 2 never wraps: below 1280 px the switcher captions are hidden, and long names are cut with an ellipsis.
- The Project and Scenario switchers are menu buttons named "Project: <name>" and "Scenario: <name>". Their menus list the choices as radio items, then the actions on the current item. Choosing another project or scenario passes through the same unsaved-changes guard as a tab change.
- Scope selectors are native `<select>` elements inside `ContextField`, each with an explicit `aria-label` equal to its visible label (sentence case): Route; Day and Direction on Trips; Trip profile, Blocking scenario, and Day on Blocking; Blocking scenario, Trip profile (read-only), and View year on Costing. Blocking and Costing render theirs into the scope bar through a portal (`scopeSlot` prop).
- A route's selector text is its short name, or "short — name" when another route has the same short name. The selector's `title` is the full route name.
- The status line, by priority: "Read-only: open in another tab"; "Local save failed"; "Saving locally…"; otherwise "Saved locally · backup N days old" (or "no backup yet"), in the warning colour when the backup is older than seven days or missing. The logic is `headerStatus` in `src/ui/shell/headerStatus.ts`.

## Phase 4 implemented Blocking conventions

- Blocking uses Trip Profile, Blocking Scenario, selected Route, and Day as context. The selected Route filters candidate Trips but never hides or truncates activities in the selected Block.
- Blocking Scenario is a named all-service-day arrangement. Its Profile relationship is immutable. Empty-create, duplicate, rename, and delete actions must state their complete scope.
- Trips adds a Blocking Scenario selector filtered to the selected Trip Profile. Its Block column is the assignment control of Decision 0025 (it was read-only under Decision 0021) and reflects only that selected arrangement. The selector is non-authoritative UI context and follows the Phase 3R menu, checked-item, focus-return, dismissal, wrapping, and responsive rules.
- The Blocking workspace uses the established `workflow-section` and `data-grid` roles. Its implemented layout places Unassigned Trips and Current Block side by side, then the Block list and selected-day summary below; React presents application-service results without calculating ownership, compatibility, findings, or summaries.
- Every Blocks table column is sortable. Selecting a Block in Current Block is activated only by clicking its name; the row may indicate the active Block but is not itself a control. The Blocks table footer shows aligned known subtotals for Revenue, Platform, Layover, Layover %, and Deadhead. Incomplete status exposes its findings on hover and keyboard focus. The Current Block selector highlights its selected menu item in blue, matching the Route Pattern selector.
- Assignment, atomic reassignment, removal, ordering, and activity editing must be completely keyboard operable. Drag-and-drop cannot be the only method.
- Operationally infeasible Blocks remain visible with planner-facing text and accessible status. Color is supplemental. Structural command rejection must identify the record and required correction.
- The selected Block always shows its complete ordered activity list, including every Route represented in imported multi-route data. Phase 4 prevents new cross-route assignment to non-empty Blocks.
- Block-level status and findings identify incomplete or infeasible work. The selected-day summary shows service quantities without separate complete/incomplete count tiles; valid but incomplete Blocks contribute known hours, and incomplete mileage is not displayed as zero.
- Dense Blocking tables retain compact controls, horizontal overflow, stable identifying columns, predictable focus after dialogs and writes, and usable desktop and narrow-width layouts.

The section "Phase 1 route definition" has since received bullets for the Route draft editors, the dialogs and menus, the Trips and Runtime action layers, and the accessibility baseline, and "Phase 2 trip building" and "Phase 4 manual blocking" received later ones. ## Phase 1 route definition

- Dense tables commit text and numeric edits on blur. This avoids local-save writes racing with active keyboard entry. Enter commits numeric values; Escape restores the saved value. Select changes and explicit actions commit immediately.
- Numeric fields retain their last saved value when blank or invalid input is left in the field, show an announced inline error, and treat zero as a valid value.
- Wide tables scroll horizontally on narrow screens. The left identifying column remains frozen on desktop table scroll.
- Removing a Node or a Pattern point is a draft change, not a modal confirmation. A removed Node row shows **Will be deleted** with **Undo**; the removal is applied by **Save nodes** or **Save Pattern**, whose review states the effect on Patterns, Runtimes, Trips, and Blocks, and **Discard changes** restores the saved collection (see the Route conventions in this document, Decision 0014, and Decision 0041). The older modal confirmation for a single removal no longer exists.
- Pattern point order uses visible up and down controls. Repeated node selections are valid and are described in the empty state. Add-node and add-point actions appear after their respective lists, preserving an uninterrupted entry sequence.
- Validation is calculated by the domain layer, but message keys and rule identifiers are never shown to users. Findings are translated into concise planner-facing text. Route-level findings appear with the affected field. New blank node and pattern drafts use a required-field placeholder rather than immediate validation messages; validation remains available to later workflow checks.
- A primary tab whose prerequisite is missing is disabled with an explanatory title (Trips needs a Pattern with at least two points; Blocking needs a Route and a Trip Profile; Costing needs a Scenario). A disabled tab does not imply missing route data.
- New Project is the single, visually prominent project-creation action. The blank-project view provides only concise orientation text.
- Project, scenario, duplicate-scenario, and reverse-pattern names use compact in-app dialogs. Required-name feedback is visible, Enter submits, and Escape cancels. Dialogs without a visible field label retain a screen-reader label. Reverse creation collects a name and completes directly without a separate confirmation.
- Compact destructive actions in tables use a subtle trash icon with an accessible name and tooltip. The destructive confirmation continues to state the effect before the record is removed.
- The selected project, scenario, and route are stored as non-authoritative browser UI preferences. On startup, each identifier is checked against current local records and safely falls back when a saved selection no longer exists.

## Phase 2R safe route editing

- Nodes are edited as a local table draft. **Save nodes** is the only write action. Pending deletion rows state **Will be deleted** and offer **Undo**; **Discard changes** returns the saved collection.
- Patterns are edited one at a time as a local draft. A new, duplicated, or reverse Pattern is marked **Unsaved** and does not change Runtimes or Trips until **Save Pattern** succeeds. **Save Pattern** and **Discard changes** are disabled when the selected Pattern has no unsaved edits. New Nodes are not available in a Pattern selector until their Node draft is saved.
- The **Add pattern** action is placed at the bottom of the Pattern list so the list reads top-to-bottom as existing Patterns followed by the creation action. **New node** and **Add pattern** are disabled while a Node or Pattern save is running, so a draft is never opened in the middle of a save whose reload follows.
- Changing the Route, project, scenario, primary tab, or adding a route while a Node or Pattern draft is dirty opens **Save route changes before leaving?** with **Save**, **Discard**, and **Cancel**. Save follows the ordinary impact review; Pattern work is resolved before Node work.
- Deterministic Pattern structure changes open a **Save and rebalance** decision. New inserted points receive their predecessor's scheduled time and a zero first segment; removing an intermediate point merges the adjacent runtime segments.
- A reordered or broadly replaced Pattern opens the destructive **Save and reset service** decision. It removes only profiles, assignments, trips, historical generation records, and revenue-trip block activities owned by that Pattern. Empty blocks remain.
- A timetable-order conflict appears beside **Save Pattern** and names the conflicting Patterns and timepoints. It is not a global banner and cannot be overridden by deleting service.

## Phase 2 runtime editor

- The Trips tab becomes available after the selected route contains a pattern with at least two points. The page retains the existing project, scenario, and route context controls.
- The shared workspace row always shows Route. On Trips, it also shows Day and Direction. The Route tab shows neither Day nor Direction because Pattern editing owns direction assignment. Blocking uses Trip Profile, Blocking Scenario, selected Route, and Day but not Direction. Runtime Pattern and both Profile controls belong to their respective workflow-section headers.
- Runtime bands are compact table rows. The left band-name column remains frozen; segment columns scroll horizontally as needed. Segment headers show the originating and destination node names rather than identifiers. Each row provides a calculated **Total** runtime after the final segment, followed by Duplicate and Remove actions. Total is the sum of the band’s segment durations and updates as valid segment edits are committed. Duplicate inserts a fresh unsaved row immediately below the source with the same timing values.
- Profile edits are local to the editor until the user selects **Save**. This permits an incomplete new row or temporarily invalid band boundary without persisting unusable data. Runtime **Actions** contains **Add Time Band** and Route-wide day copy. **Discard** and **Save** appear in the header only when the editor is dirty. The domain validator supplies planner-facing findings at save time.
- Runtime time and duration fields use 24-plus `H:MM` input. Blur and Enter commit a valid value; Escape restores the previous value. A blank duration states that a runtime is required and that zero remains valid.
- New and copied profiles are explicitly named in a dialog. A copied profile is independent and is assigned to the current service day. Reverse-copy is offered only for a compatible reversed node sequence; it identifies the target pattern and states that segment runtimes will be reversed.
- No generated trips exist at this package. Band-boundary edits therefore do not claim a trip impact. The later trip-generation workflow will surface departures that fall into intentional runtime gaps.
- When there is no usable pattern, the Trips tab explains the prerequisite instead of exposing an incomplete editor.

## Shared workflow and table hierarchy

- A full-page planning workflow uses vertically stacked `workflow-section` panels. Service, Runtimes, Trips, Blocking, and future Costing panels use the same white background, neutral border, compact 12px padding, and thin dark-blue top rule.
- Each workflow section has one compact header area for its title, supporting instruction, and actions. Do not add a second ordinary card inside a workflow section solely to contain the controls or table.
- A dense table is a `data-grid` viewport: it has a neutral one-pixel frame, horizontal scrolling when required, and an 8px separation from the preceding content. The grid frame contains the table header and body; its grey header is not a competing section boundary.
- Notices, prerequisites, and destructive-impact messages use an accent treatment only when they communicate state. They are not substitutes for ordinary workflow sections or data-grid frames.
- Blocking: removing a Trip, Pull-out, or Pull-in from a Block asks first through the Confirm dialog and names the activity; deleting a Block or a Blocking Scenario shows what it removes (Trips, deadheads, and activities, or Blocks and activities, from `previewDeleteBlock` and `previewDeleteBlockingScenario`) and deletes with the reviewed source signature, closing the dialog if the source changed. A Trip from another Route shows that Route's short name before its Pattern name in the Pattern pill (`31B · Pattern`); a Trip of the selected Route shows the Pattern name alone. Pills carry the full name as a tooltip. Block hours and miles use the Costing rounding (two decimals, half away from zero). "Move Trip N" counts Trips only, and "No current issues." is a plain note, not a warning. Blocking loads apply only the latest response.
- Every modal dialog is built by `ModalDialog` (`src/ui/ModalDialog.tsx`), which follows the WAI-ARIA modal dialog pattern: focus moves to the control marked `autoFocus` or to the first focusable control; Tab and Shift+Tab stay inside, and focus that escapes is pulled back; Escape cancels unless the dialog is busy; on close, focus returns to the control that opened it (for a menu item, the menu's trigger). Each dialog has an accessible name (`labelledBy` the heading id, or `label`). A submitting dialog is a dialog section that holds a form. A menu item that opens a dialog never refocuses its trigger.
- Menus (`MenuButton`): a choice among alternatives is `menuitemradio`; an independent toggle (`kind: 'checkbox'`, the Display options) is `menuitemcheckbox`; Escape returns focus to the trigger at once; Tab closes an open menu and moves on. After an action removes or disables the control that was used (Shift drawer steps, Discard in the Runtime or Node editor), focus goes to the pressed control or to a neighbour in the same area, never to the page.
- Accessibility baseline checked by `tests/ui/keyboard.spec.ts` with axe-core: dialog names, labels, one `main` landmark, one `h1` per workspace (a visually hidden `h1` where the screen shows no visible one), `scope="col"` on table column headers, `aria-invalid` and `aria-describedby` on a field that shows an error, and a labelled file input.
- Unsaved input is never dropped silently. A Runtime profile with unsaved edits asks Save, Discard, or Cancel before the Runtime Pattern or Profile, the service day, the Direction, or the tab changes, and the browser's leave prompt covers a reload. A staged Shift asks to be discarded before any of those changes and before a Runtime save, because a save reloads the Trips; with both open, the Runtime question comes first. An Add-trip row that has a Pattern or a first time entered asks Cancel or Discard before the service day, the Direction, the Trip Profile, or the tab changes (after the Runtime and staged-Shift questions, one question per press); an empty row is dropped without a question, and a Runtime save keeps the row. Build Trips closes without a prompt and keeps its values for the next time it is opened (a successful build clears them). Saving Nodes keeps an unsaved Pattern draft, and saving a Pattern keeps unsaved Node edits. Escape in a numeric or runtime time field restores the saved value and writes nothing.
- Stored selections (`localStorage`) are checked field by field: a value of the wrong shape reads as not stored. The Blocking Scenario chosen in Trips and in Blocking is remembered for each Trip Profile.
- Delete dialogs close when the deletion is refused (a stale review, Decision 0041) and show the refusal in the error banner; nothing is deleted, and a new review shows the current impact. This holds for Route, Scenario, Project, Pattern, Runtime profile, and Trips deletion. The Node save review also lists the pull-out, pull-in, and deadhead activities the save removes ("Removes 3 pull-out, pull-in, or deadhead activities in 2 Blocks."), and the Trip Profile delete confirmation says "Also deletes 2 Blocking Scenarios and their Blocks." ("1 Blocking Scenario and its Blocks" for one) when the profile owns any; both lines are absent at a count of 0.
- The Project menu shows the last backup time and, when the browser did not grant persistent storage (refused or unsupported), a second line under it: "This browser may clear local data. Export backups regularly." Nothing is added when storage was granted or the browser has not been asked yet (it is asked after the first successful save).
- Error text shown to a planner comes from the application's own wording through `userFacingError` (`src/ui/errorMessages.ts`); technical text from the browser, Dexie, or JavaScript, and raw message keys, are never shown. A failure message says what did not happen and what to do next. A read-only tab shows an information notice (`notice info`) and "Read-only" in the header; edit controls stay visible and writes are rejected.
- New UI elements must use these roles before introducing a new bordered box style. A different container treatment requires a functional reason, such as a modal decision, a nested list/detail editor, or a state-specific notice.
- Runtimes and Trips use one upper-right header action layer. A Profile menu lists saved profiles first, marks the selected Profile, and separates lifecycle commands from selection. Runtime Pattern remains a native labeled selector because it is Pattern-owned. Runtime **Actions** groups the Route's calculation method (**Method (all Patterns on this Route)**, changed through a confirmation that states the profiles and Trips affected; Decision 0045), runtime editing, CSV export, and service-day copy. Runtime-profile CSV and Trips-table CSV exports stay in their owning workspace's **Actions > Data** group; neither has an import. Runtime profile export is unavailable while its editor has unsaved changes because export uses the saved profile.
- View menus for Runtime Profile, Trips Profile, Trips Scenario, and Blocking Scenario use the same small bold field label above the selected value. Lifecycle commands such as New, Copy, Rename, and Delete remain quasi-button actions within the menu and are visually distinct from view selection.
- The Trips **Actions** menu groups Display options, Schedule commands, service-day copy, CSV export, and selected-Trip deletion. The copy action is labeled **Copy Trips from day** to distinguish it from **Copy profile**. Selection-dependent commands remain visible and disabled with an explanation. **Regenerate selected…** is always listed and acts only on selected Trips with changed runtimes, so select-all is safe. **Undo last regeneration (N Trips)** is a separate item directly after it, listed only while the saved undo applies to the visible schedule (Decision 0046). The row trash icon and bulk Delete use the same impact-aware deletion confirmation.
- Trips uses page-level vertical scrolling. When the schedule headings move above the viewport, a fixed duplicate heading row appears at the top and stays aligned with the table's measured column widths. Its horizontal scroll position follows the data grid, and no nested vertical scroll area is used.
- Build Trips opens a non-modal drawer docked to the right edge of the application, matching Shift Trips. It has Pattern, First Trip, Headway, Number of Trips, Last Trip, resolved runtime-profile context, Build, and Cancel. Number of Trips and Last Trip are mutually exclusive: entering either disables the other. Last Trip includes a departure that falls exactly on the headway sequence. A request is bounded to 500 Trips whichever of the two limits is used: Number of Trips may not exceed 500, and Last Trip may not produce more than 500 departures.
- When saved trips use earlier runtimes, `Run Times Have Changed` remains visible immediately above the table. When the assigned Runtime profile cannot calculate one or more of the affected Trips, a plain status line (`role="status"`) directly under it gives their count and each distinct reason once, for example "2 Trips cannot be recalculated. No Runtime band covers its first departure. Add or extend a Runtime band." Nothing is shown when every affected Trip can be recalculated. A visible `Run times changed` note marks each affected row, and **Regenerate selected** is enabled only when an affected row is selected.
- Shift opens a non-modal compact panel docked to the lower right edge of the application, 16 px in from the edge and the bottom, 320 px wide and only as tall as its content, so the Trips table stays visible (U10). It shows the net shift ("2 minutes later") and the selection count as a status, two step buttons that name their size and direction ("← 5 min earlier", "5 min later →"), and a **Step** radio group of 1, 5, 10, and 15 minutes beside a **Step minutes** field for any other whole number of minutes; an invalid step disables both step buttons and says why. Each press creates a transient signed minute operation; Undo and Redo apply only to that drawer operation sequence. The table shows the staged times and text status before **Done** makes one atomic write. **Discard**, Close, or Escape write nothing. Route, Day, Direction, Trip Profile, tab, and selection changes request discard before changing scope. A stale preview requires discard and reopening Shift.
- Target-first copy dialogs keep the selected Day fixed, name the affected scope once, and require a preview before commit. Destructive empty-source Trip copies require an explicit clear-target acknowledgement and use the destructive confirm treatment.
- Batch actions retain checked rows on cancel and return focus to their trigger. A reviewed batch preview names every selected record as eligible or ineligible; confirmation is unavailable when any selected record is ineligible.

## Phase 2 trip building

- The Trips workspace is vertical: the runtime editor is first and the combined materialized schedule is last. This keeps the runtime prerequisite visible while making the generated schedule the working surface. (The generation-set editor that sat between them is gone: see the next bullet.)
- **Superseded by Decision 0010 and removed in review package X01:** the generation-set editor names and selects a saved set, then exposes pattern, first departure, headway, and one explicit generation limit. The end-time option is labeled **Inclusive end time** so a departure at that time is expected. Existing sets are loaded into the editor; choosing one prepares its next generation revision locally and does not write until confirmation.
- Generation and regeneration always open a preview dialog. The dialog summarizes additions, changes, removals, overridden shifts or pattern changes, and affected future block references before it offers a confirm action. Escape and Cancel close the dialog without a write.
- The combined schedule selects one service day and interlaces all trips in the selected direction. When patterns share a timetable column, rows sort by the earliest common timepoint; schedules without a common column fall back to initial departure. It uses fixed compact summary columns and reveals scheduled points through a per-trip detail row instead of creating unlimited timepoint columns. This keeps alternating, staggered, short, and full-length patterns visible in one table without doubling long schedules by default.
- Multi-trip selection uses visible checkboxes in the frozen first column. Shift-clicking a second checkbox selects the inclusive range between the last non-shift selection and that row, using the rows currently visible in the table; the header checkbox selects or clears all visible rows. A signed whole-minute shift is applied to all checked trips. Keyboard users can operate each native checkbox and retain table focus after the schedule reloads.
- Pattern changes are individual-trip actions. The user chooses a target pattern, then sees old and recalculated timepoints in a second preview before confirmation. The target pattern must have a runtime profile assigned for the current service day.
- Generated trips show **Generated**. Shifted and pattern-changed trips show an amber status marker with an explanatory label. The Block column is scoped to the selected Blocking Scenario. Its pill provides same-day Block choices and a confirmed unassign option; the Trips Actions menu supports confirmed multi-Trip assignment and unassignment.

## Phase 4 manual blocking

- **Blocking** is a primary workspace after Route and Trips. Its upper context layer identifies Trip Profile, Blocking Scenario, and service day. The selected Route remains in the shared workspace row and filters only candidate Trips.
- The workspace presents **Unassigned Trips** and **Current Block** side by side on wide layouts, with additional width allocated to Current Block so its standard columns fit without horizontal scrolling at ordinary desktop widths. The Current Block header right-aligns a labeled Block selector and an **Actions** menu. The selector lists Blocks for the selected day; Actions contains Block lifecycle and notes commands, pull-out/pull-in creation, and selection-dependent Trip reassignment and removal. The Block table always displays the complete ordered activity list, including imported activities outside the selected Route. The lower row shows Block status and a selected-day summary; its Trips count includes revenue Trips only.
- Empty Blocking Scenarios and empty Blocks are valid states with direct creation actions and explanatory empty-state text. Scenario and Block deletion use explicit confirmation dialogs that name their complete scope and consequences.
- Unassigned Trips offers a compatible-only filter for the Block's implicit appended revenue position. Its compact Pattern, Start, From Time, To Time, End, and Assign columns mirror the relevant Current Block fields. Assign buttons communicate compatible, deadhead-needed, conflict, and incomplete states.
- Unassigned Trips does not expose a placement selector; ordinary Assign adds a Trip at the end of current revenue work, before any pull-in. Its **Actions** menu contains the checked **Compatible only** display filter and a Minimum layover dialog. The minimum can be a fixed number of minutes per connection or a percentage of the preceding Trip's revenue runtime; it is a browser UI preference used to classify candidates and does not modify persisted Blocks. Current Block uses a leading multi-select checkbox column followed by #, Pattern, Start, From Time, To Time, End, Deadhead, Layover, and Actions. The # column numbers revenue Trips only. Its Deadhead cell presents a compact plus icon for each eligible connection, then a clickable saved duration. Pull-out and pull-in editing uses a relative whole-minute offset from the adjacent revenue Trip. The deadhead dialog can apply its values to matching consecutive From/To Node pairs in the current Block; Layover remains the separately derived remainder. Revenue Trips and boundary activities use the same circled-X removal icon; multi-Trip reassignment and removal are atomic Actions-menu commands.
- The Current Block selector orders Block labels by natural numeric/alphabetic order. Standalone deadhead activity rows are not repeated in the table; their values are represented on the preceding revenue-Trip row.
- Native buttons support assignment, reassignment, removal, ordering, activity editing, and destructive actions. Drag-and-drop is not required for any Phase 4 operation. Unassigned Trips and Current Block use the same inclusive shift-click range-selection behavior over their visible Trip rows. Disabled selection-dependent actions remain visible and state why a selection is required.
- Multi-file CSV exports are delivered as one ZIP download containing the stable CSV files. A single export click must not initiate multiple independent downloads that desktop file associations may open in separate spreadsheet windows.
- Activity and summary findings use text status in addition to color. Finding links provide a keyboard-operable return path to the selected Block. Activity and schedule tables retain the `data-grid` frame and horizontal overflow on narrow layouts.
- Trips adds a labeled **Blocking Scenario** selector immediately beside its existing labeled **Profile** selector (glossary term; the label was "Scenario" before review package U07, which the global Scenario selector also uses). It is filtered to that Trip Profile and scopes the Block assignment pill and bulk Actions. **No Blocking Scenario** appears only when no scenario exists or the selected scenario was removed. Changing this selector does not alter Trip editing scope.
- Block summaries report **Revenue** as Running Time plus usable Layover, while retaining **Running** as the sum of scheduled revenue-Trip durations. Selected-day summary tiles show service quantities without repeating complete/incomplete Block counts; each Block’s own status and findings remain in the Blocks table.
- All trip time fields, summaries, and previews use shared 24-plus service-time formatting. The schedule never converts after-midnight service to a wrapped clock time.
