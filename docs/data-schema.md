# Initial Data Schema

## Purpose

This document defines the planned TypeScript entity shapes and IndexedDB table boundaries. Phase 1A implements these entity shapes in `src/domain/types.ts`. Exact syntax may change during scaffolding, but changes to relationships or ownership require an architectural review.

## Schema conventions

- IDs are UUID strings generated by the application.
- Times and durations are integer seconds.
- Distances are non-negative decimal miles.
- Currency codes use ISO 4217 strings such as `USD`.
- Persisted timestamps use ISO 8601 strings.
- Ordered child records use explicit `sequence` values and stable child IDs.
- Nested arrays are used when children are always loaded and saved with their parent.
- Cross-entity relationships use IDs rather than copied records.
- Derived summaries and current validation results are not persisted as source data.

## Value types

```typescript
type EntityId = string;
type IsoTimestamp = string;
type ServiceSeconds = number;
type DurationSeconds = number;

  | "weekday"

```

Runtime guards must confirm that seconds are integers and that distances are finite, non-negative numbers.

## Project and scenario entities


Deleting a project requires explicit confirmation and cascades through its scenarios. Deleting a scenario requires explicit confirmation and cascades through scenario-owned records.

## Service-day entity

```typescript
interface ServiceDayDefinition extends EntityMetadata {
  id: EntityId;
  scenarioId: EntityId;
  kind: ServiceDayKind;
  name: string;
  annualServiceDays: number;
  sequence: number;
}
```

The four standard service days are created for a new scenario. Annual service days must be a non-negative integer. The application may warn if their sum does not match the analysis-year calendar but must not silently change them.

## Route patterns

```typescript
interface PatternPoint {
  id: EntityId;
  nodeId: EntityId;
  sequence: number;
  cumulativeMiles: Miles;
  directionColumnId?: EntityId;
}

interface RoutePattern extends EntityMetadata {
  id: EntityId;
  scenarioId: EntityId;
  routeId: EntityId;
  name: string;
  directionId?: EntityId;
  sequence?: number;
  directionLabel?: string;
  notes?: string;
  points: PatternPoint[];
}

interface ProjectSnapshot {
  project: Project;
  scenarios: Scenario[];
  serviceDays: ServiceDayDefinition[];
  routes: Route[];
  nodes: Node[];
  patterns: RoutePattern[];
  directions?: RouteDirection[];
  runtimeProfiles: RuntimeProfile[];
  runtimeAssignments: RuntimeAssignment[];
  /** Scenario-wide timetable alternatives. */
  tripProfiles: TripProfile[];
  /** Historical Phase 2 collection; current authoritative exports leave it empty or omit it. */
  generationSets: TripGenerationSet[];
  trips: Trip[];
  blocks: Block[];
}
```

Pattern validation requires:

- at least two points;
- unique pattern-point IDs;
- contiguous sequence values after normalization;
- existing node references;
- a first cumulative distance of zero;
- non-decreasing cumulative distance;
- repeated node IDs are allowed.

Reverse-pattern creation reverses point order, creates new pattern-point IDs, and reconstructs cumulative miles from reversed segment distances.

## Runtime entities

Runtime entities are not implemented in Phase 1, but their relationships constrain the route-pattern model.

```typescript
interface RuntimeBand {
  id: EntityId;
  label: string;
  sequence: number;
  startTime: ServiceSeconds;
  endTime: ServiceSeconds;
  segmentRuntimeSeconds: DurationSeconds[];
}

interface RuntimeProfile extends EntityMetadata {
  id: EntityId;
  scenarioId: EntityId;
  routeId: EntityId;
  patternId: EntityId;
  name: string;
  bands: RuntimeBand[];
  calculationRevision?: number;
}

interface RuntimeAssignment extends EntityMetadata {
  id: EntityId;
  scenarioId: EntityId;
  patternId: EntityId;
  serviceDayId: EntityId;
  runtimeProfileId: EntityId;
}
```

Each runtime band must contain exactly `pattern.points.length - 1` segment values. Runtime assignments must be unique by pattern and service day.

Phase 2R-B adds `RuntimeProfile.calculationRevision`. It starts at zero for a new or copied profile and increments when runtime bands or segment values change; renaming a profile does not increment it. Package 2R-C records the profile ID and revision used for each trip's current scheduled points.

## Trip generation and trip entities

Decision 0016 defines the scenario-wide Trip profile layer implemented in Phase 2TP. The definitions below describe the current Trip-profile schema.

```typescript
interface TripProfile extends EntityMetadata {
  id: EntityId;
  scenarioId: EntityId;
  name: string;
  sourceTripProfileId?: EntityId;
}
```

```typescript
type GenerationLimit =
  | { mode: "endTime"; endTime: ServiceSeconds }
  | { mode: "tripCount"; tripCount: number };

/** @deprecated Historical persisted generation input. New requests are transient. */
interface TripGenerationSet extends EntityMetadata {
  id: EntityId;
  scenarioId: EntityId;
  routeId: EntityId;
  serviceDayId: EntityId;
  patternId: EntityId;
  name: string;
  firstDeparture: ServiceSeconds;
  headwaySeconds: DurationSeconds;
  limit: GenerationLimit;
  generationRevision: number;
}

interface GenerateTripsRequest {
  scenarioId: EntityId;
  tripProfileId: EntityId;
  routeId: EntityId;
  serviceDayId: EntityId;
  patternId: EntityId;
  firstTrip: ServiceSeconds;
  headwaySeconds: DurationSeconds;
  lastTrip: ServiceSeconds;
}

interface AddTripRequest extends Omit<GenerateTripsRequest, "headwaySeconds" | "lastTrip"> {
  directionId: EntityId;
}

interface ScheduledPoint {
  patternPointId: EntityId;
  sequence: number;
  time: ServiceSeconds;
}

interface TripProvenance {
  kind: "generated" | "manual";
  creationMethod?: "generated" | "manual";
  generationSetId?: EntityId;
  generationRevision?: number;
  generationSequence?: number;
  manuallyChangedFields: Array<"patternId" | "times">;
  /** Net signed shift applied to generated stop times, in seconds. */
  manualTimeShiftSeconds?: DurationSeconds;
  runtimeProfileId?: EntityId;
  runtimeCalculationRevision?: number;
  calculationSource?: {
    runtimeProfileId: EntityId;
    runtimeCalculationRevision: number;
  };
}

interface Trip extends EntityMetadata {
  id: EntityId;
  scenarioId: EntityId;
  tripProfileId: EntityId;
  routeId: EntityId;
  serviceDayId: EntityId;
  patternId: EntityId;
  publicLabel?: string;
  stopTimes: ScheduledPoint[];
  provenance: TripProvenance;
}
```

Generation requests are not saved. `generateTrips` inserts all calculated trips in one transaction and never replaces existing trips. `Add Trip` inserts one trip using the selected pattern's assigned profile. Possible exact duplicates are warnings. Pattern changes and recalculation retain trip IDs; recalculation impact includes manual fields and block references. A trip is stale when its recorded calculation source differs from the currently assigned profile or revision.

## IndexedDB tables and indexes

The initial Dexie database should use a unique application-specific name. Proposed tables are:

| Table | Primary key and useful indexes |
| --- | --- |
| `projects` | `id`, `name`, `updatedAt` |
| `scenarios` | `id`, `projectId`, `[projectId+name]`, `updatedAt` |
| `serviceDays` | `id`, `scenarioId`, `[scenarioId+kind]`, `sequence` |
| `routes` | `id`, `scenarioId`, `[scenarioId+name]`, `updatedAt` |
| `nodes` | `id`, `scenarioId`, `routeId`, `[routeId+name]` |
| `patterns` | `id`, `scenarioId`, `routeId`, `[routeId+name]` |
| `directions` | `id`, `scenarioId`, `routeId`, `[routeId+name]` |
| `runtimeProfiles` | `id`, `scenarioId`, `routeId`, `patternId` |
| `runtimeAssignments` | `id`, `scenarioId`, `patternId`, `serviceDayId`, `[patternId+serviceDayId]` |
| `generationSets` | historical Phase 2 table; no new authoritative writes |
| `tripProfiles` | `id`, `scenarioId`, `[scenarioId+name]`, `updatedAt` |
| `trips` | `id`, `scenarioId`, `tripProfileId`, `routeId`, `serviceDayId`, `patternId`, `[tripProfileId+routeId]`, `[tripProfileId+serviceDayId]`, `provenance.runtimeProfileId` |
| `blocks` | `id`, `scenarioId`, `tripProfileId`, `serviceDayId`, `[tripProfileId+serviceDayId]`, `[serviceDayId+label]` |
| `costPlans` | `id`, `scenarioId`, `[scenarioId+name]` |
| `appMetadata` | `key` |

Dexie index syntax must be verified during implementation. Compound uniqueness that IndexedDB cannot enforce directly must be checked in domain or repository commands.

## Repository interfaces

The application layer should depend on narrow interfaces rather than the Dexie database class.

```typescript
interface RouteDefinitionRepository {
  listProjects(): Promise<Project[]>;
  getProject(projectId: EntityId): Promise<Project | undefined>;
  saveProject(project: Project): Promise<void>;
  listScenarios(projectId: EntityId): Promise<Scenario[]>;
  saveScenario(scenario: Scenario): Promise<void>;
  getScenarioRecords(scenarioId: EntityId): Promise<ScenarioRecords | undefined>;
  saveScenarioRecords(records: ScenarioRecords): Promise<void>;
  commitRouteEdit(records: ScenarioRecords): Promise<void>;
  getRouteDefinition(routeId: EntityId): Promise<RouteDefinitionAggregate | undefined>;
  saveRouteDefinition(aggregate: RouteDefinitionAggregate): Promise<void>;
  listDirections(routeId: EntityId): Promise<RouteDirection[]>;
  getProjectSnapshot(projectId: EntityId): Promise<ProjectSnapshot | undefined>;
  saveProjectSnapshot(snapshot: ProjectSnapshot): Promise<void>;
}
```

Exact interfaces should follow use cases. Do not create a generic repository abstraction that hides required transaction boundaries.

The authoritative trip repository exposes trip, block, pattern, assignment, and runtime-profile queries plus atomic `insertTripsAtomically` and `saveTripChangesAtomically` operations. Package 3A adds optional structural repository commands `commitRuntimeCopyAtomically` and `replaceTripsForDayAtomically`; both validate the complete affected graph before writing and execute one transaction. Runtime-copy and Trip-copy previews carry source signatures that the application recalculates immediately before commit. The historical generation-set repository methods remain only for the running pre-2R UI and are not used by the revised commands.

## Transactions

Use one transaction for operations that must remain consistent, including:

- creating a scenario and its standard service days;
- cloning a scenario and all owned records;
- deleting a scenario;
- saving a route with node and pattern changes that affect references;
- committing a reviewed Node or Pattern edit with reconciled directions, runtimes, trips, and affected blocks;
- regenerating a trip set and updating affected block references;
- importing a complete project backup.

## Database versions and migrations

The first implementation starts at database version 1. Version 2 adds a non-unique `runtimeProfileId` index to `runtimeAssignments` for profile lifecycle queries. Phase 2TP increments the database to version 3 with a `tripProfiles` store and Trip-profile ownership indexes on Trips and Blocks. Each later schema change must:

1. increment the database version;
2. define an explicit migration;
3. preserve existing user data or fail without partial writes;
4. include a migration test;
5. update this document when entity meaning or ownership changes.

`appMetadata` should include the application data-schema version used by JSON exports. Database version and export-schema version are related but distinct.

## Backup schema

A JSON backup contains:

- format identifier;
- export-schema version;
- export timestamp;
- application version when available;
- one complete project graph: the project, scenarios, service days, routes, nodes, directions, patterns, pattern points, runtimes, generation sets, trips, and blocks.

The current export schema is version 4 and stores directions, runtime profiles, assignments, Trip profiles, trips, and blocks as top-level arrays. Empty authoritative exports omit the historical `generationSets` property; populated historical records remain readable for transition purposes. Version 1 through version 3 imports are normalized to one Default Trip profile per Scenario.

Import must validate the complete payload before opening a write transaction. ID collision policy must be explicit: replace an existing project only after confirmation, or import with remapped IDs as a new project.

## CSV exports

Phase 1 should export:

- routes;
- nodes;
- patterns;
- pattern points.

Phase 2R adds runtime bands, directions, direction columns, authoritative trips, scheduled points, blocks, and block activities. Phase 2TP adds `tripProfileId` and `tripProfileName` to the Trip and Block CSV outputs. The authoritative trip CSV contains creation method and runtime calculation source fields and does not include generation-set columns. A legacy export method remains temporarily for the pre-2R UI. CSV files are reporting and exchange outputs, not full backups.
