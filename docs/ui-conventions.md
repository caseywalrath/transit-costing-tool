# UI Conventions

## Phase 3R acceptance

The Runtime and Trip header-action conventions below are implemented and accepted through Phase 3R. They retain separate Runtime and Trip scopes, preserve the existing shared workflow-section system, and do not establish a convention for top-level Scenario/Data menus or Route-tab Node/Pattern menus.

## Interface revision (Phase UR, Decision 0047)

This section holds the conventions of the interface revision (packages UR-0 to UR-11, `docs/implementation/ui-revision-plan.md`). Where an older bullet later in this document disagrees, this section wins; the older bullets that it replaced have been deleted or rewritten.

### Tokens, type, and formats

- `src/ui/styles/tokens.css` is the only stylesheet that holds raw colour values. Component rules use the token names for colour, font size, weight, spacing on the 4/8/12/16/24 px scale, control and row height, radius, and shadow. Three role tokens cover the spacing between the scale steps: `--space-inline` (6 px: between a label and its control, an icon and its text, the items of a compact bar), `--inset-tight` (10 px) and `--inset-panel` (14 px) for the padding inside panels and bars; `--font-size-chip` (12.5 px) is the chip and pill text. Raw pixel values remain only for control geometry (fixed widths and heights, and the paddings that clear a fixed-size button) and in rules written before Phase UR; convert a legacy rule when it is changed.
- The typeface is Source Sans 3 (variable), bundled through `@fontsource-variable/source-sans-3` and imported in `src/main.tsx`; the application makes no font request to the network. Numeric cells use tabular digits.
- Screens format numbers with `src/ui/format.ts` (F1–F8): `formatClock` (`4:08`, `26:01`), `formatDuration` (`:53` under an hour, `1:01` from an hour), `formatHours` (two decimals daily, whole annual), `formatMiles`, `formatMoney` (whole dollars, cents for the hourly rate), `formatPercent` (one decimal), `withUnit`, and `MISSING` ("—") for not applicable. Missing input shows the amber word "Incomplete". Table headings carry the unit ("Running (h)"); cells do not. CSV and backup files keep their own formatters and do not use these.
- Editable runtime cells keep the `:MM` entry grammar for an hour or more (`:61`), because `1:01` means one minute one second there (O-3).

### Surfaces and actions

- Three surface levels, built only through the components in `src/ui/shared/surfaces.tsx`: **WorkSurface** (level 1: white panel, title, optional count, badge, context selectors, subtitle, and actions in one header), **SupportPanel** (level 2: muted title over a tinted box, no card border), and **InlineNote** (level 3: an icon and one line of text; kinds info, warn, ok). The collapsible Runtimes section builds the WorkSurface markup by hand because its title is a disclosure button.
- A panel has at most one primary button. Frequent actions are visible labelled buttons in the panel header; rare and destructive actions are in the panel's "⋯" menu; actions on selected rows are in a **SelectionBar** (`role="toolbar"`, "N <noun>s selected", the commands, Clear), shown only while rows are selected.
- Compact cell labels use `Chip`; Block labels use `BlockPill` (a dot in the Block's hashed colour from `blockColorToken`, and the label as text, so the colour is never the only signal).
- **Save rule.** A standalone field (a name, a service-day count, a selector) saves when it is committed. A table or grouped form (Nodes, Pattern, Runtimes, Costing assumptions) collects edits and shows a **SaveBar** at the bottom of its panel only while it has unsaved edits: a message with the count from `src/application/draftChangeCounts.ts`, **Discard**, and the save button. Impact reviews and navigation guards are unchanged.

### Short names

- The Trips and Blocking tables show a Pattern's short name in its chip or pill and keep the full name as the tooltip. The short name is the one entered in the Pattern editor's **Pattern short name** field (stored as `directionLabel`); when it is empty, `patternShortName` in `src/application/shortNames.ts` generates one from the full name: the direction abbreviation (Northbound → NB, Southbound → SB, and so on; initials for a direction of several words), then "<origin>–<destination>" for a name of the form "<origin> to <destination>", using an end Node's short name when the part names that Node and shortening street and place words otherwise ("Northbound: Evans to Wagon Road" → "NB Evans–Wagon Rd"). That field shows the generated name as its placeholder. Generated names are never stored.
- The Blocking tables (Unassigned trips and Current block) show each Start and End Node by its short name, or, when it is empty, by its name with street and place words after the first word shortened (`nodeShortName`), with the full name as the tooltip. The Nodes table shows that generated name as a placeholder in an empty Short cell when it differs from the name.
- Reversing or duplicating a Pattern does not copy its short name.

### Interface text

- Interface text uses sentence case with lower-case domain terms mid-label ("Blocking scenario", "Unassigned trips", "Assign block…"). The tab names Route, Trips, Blocking, and Costing stay capitalized. "Profile" is always qualified ("Runtime profile", "Trip profile"). The Costing escalation field is "Inflation rate (%)". The documentation keeps its capitalized domain terms. CSV headers, message keys, `ruleId`s, and the persistence layer's error messages are not interface text and keep their wording.

### Accessibility

- Every link, button, input, select, textarea, summary, and element with a `tabindex` shows a 2 px `--color-focus` outline with a 2 px offset on `:focus-visible` (`src/ui/styles/base.css`). Grid cells show an inset 2 px ring instead.
- Pointer targets are at least 24 × 24 px, or keep a 24 px spacing circle clear of other targets (WCAG 2.2 target size). Icon buttons are 26 or 28 px; the Blocking column-filter buttons are 24 px.
- `tests/ui/keyboard.spec.ts` runs axe-core with `color-contrast` and `target-size` in addition to the baseline rules on all four tabs and on the open project, profile, and trip dialogs; a new screen or dialog is added to that run.

### Application header (UR-5)

- The header has two rows. Row 1 (`app-bar`) holds the application name, the primary tabs (`aria-current="page"` on the active one), and one status line. Row 2 (`scope-bar`, region "Scope") holds the Project and Scenario switchers, a divider, the active tab's scope selectors, and the tab's "⋯" menu. Row 2 never wraps: below 1280 px the switcher captions are hidden, and long names are cut with an ellipsis.
- The Project and Scenario switchers are menu buttons named "Project: <name>" and "Scenario: <name>". Their menus list the choices as radio items, then the actions on the current item. Choosing another project or scenario passes through the same unsaved-changes guard as a tab change.
- Scope selectors are native `<select>` elements inside `ContextField`, each with an explicit `aria-label` equal to its visible label (sentence case): Route; Day and Direction on Trips; Trip profile, Blocking scenario, and Day on Blocking; Blocking scenario, Trip profile (read-only), and View year on Costing. Blocking and Costing render theirs into the scope bar through a portal (`scopeSlot` prop).
- A route's selector text is its short name, or "short — name" when another route has the same short name. The selector's `title` is the full route name.
- The status line, by priority: "Read-only: open in another tab"; "Local save failed"; "Saving locally…"; otherwise "Saved locally · backup N days old" (or "no backup yet"), in the warning colour when the backup is older than seven days or missing. The logic is `headerStatus` in `src/ui/shell/headerStatus.ts`.

### Route tab layout (UR-6a)

- The top row is two supporting panels of equal width: **Route details** (Route name, Short name, and Description stacked one above the other) and **Annual service days** (the Service days table with a narrow, right-aligned count column, and a "Total N of 365" line; UR-14 removed the note "Saves when you leave a field. Zero is valid."). The Service-day name stays an editable field, so the table form is kept; the plan's four-field strip would have needed a new rename interaction.
- Onboarding (UR-16). Empty states name the next action as a button, in terse text: no project ("No project", **New project…**, **Restore from backup…**); a scenario without routes ("No routes", **New route**); Costing without a blocking scenario (**Open Blocking**). The Route selector's last option, "+ New route", adds a Route; **New route** also stays in the Route actions menu. While a Route has no Pattern with 2 or more points, a **Route setup** line (`nav`) above the panels lists the steps Route name → Nodes N/2 → Pattern, 2+ points → Runtimes and trips; the current step has `aria-current="step"`, done steps a check, and each step button moves the focus to its control. While there are fewer than 2 Nodes, "+ New node" is a primary button; while there are no Patterns, "+ Add pattern" is.
- Below, **Nodes** and **Patterns** are work surfaces. "+ New node" and "+ Add node to pattern" are the last row of their tables.
- **Save rule.** Standalone fields (route details, service-day counts) save when the field is left. A table or grouped form collects edits and shows a `SaveBar` at the bottom of its panel, only while there are unsaved edits: Nodes ("N unsaved changes in Nodes", **Discard**, **Save nodes**) and the Pattern editor (**Discard**, **Review and save**, which still opens the impact review).
- The Pattern list is grouped by direction with caption rows, on a tinted (`--color-surface-2`) background. Each Pattern is a white card with a soft border; the selected one has the accent border, the accent-soft fill, and a 3 px accent bar on its left edge (UR-14). A card shows the Pattern name without its "<Direction>:" prefix (the full name is its tooltip), then its short name as a chip and "N points · total mi". The editor header shows the Pattern name, "Direction · N points · total mi", the visible **Reverse** button, and a "⋯" menu named **Pattern actions** (Duplicate pattern, Delete pattern…; a new unsaved Pattern offers Discard new pattern instead).
- Below 1100 px wide the top row and the Nodes and Patterns panels stack.

### Costing tab layout (UR-6b)

- **Costing assumptions** is a work surface (subtitle: "Shared by every blocking scenario in <scenario>"). Its fields are a three-column form labelled in sentence case, with **Inflation rate (%)**. A line under the form lists the annual service days and ends "edit on the Route tab".
- Its save bar ("N unsaved changes · the estimate below already includes them", or "Not saved yet · …" when the Scenario has no saved assumptions) appears while the form differs from the saved record. **Discard** puts the last saved values back in the form and writes nothing; **Save assumptions** keeps its validation rule. The estimate is calculated from the form, so the message says it already includes the unsaved values.
- **Cost breakdown · <year>** is a work surface. Its table headings are "Daily revenue (h)", "Daily platform (h)", "Daily cost", "Annual revenue (h)", "Annual platform (h)", and "Annual cost". "No estimate yet", "Partial estimate", and "Invalid inputs" are badges beside the title; the warning and rounding notes are inline notes.
- **Exclusions** and **Yearly outlook** are supporting panels.
- "Export costing CSV" is a visible button in header row 2 (UR-5); the Costing actions menu no longer exists.

### Trips tab layout (UR-6c, UR-8, UR-9)

- **Runtimes** is a collapsible work surface. Collapsed (the default), it is one line: a disclosure button ("▸ Runtimes", `aria-expanded`) and **Edit runtimes**. Expanded, it shows the Pattern selector in the header, then the **Runtime profile** menu, the ⋯ **Runtime actions** menu, and the editor. The disclosure button is the only control that collapses it; UR-14 removed the summary line and the **Close** button. The open state is kept per device under `transit-costing-tool.runtimes-open.v1` (`{"open": true}`; any other stored value reads as collapsed). The disclosure button is disabled, with the title "Save or discard runtime edits first", while the editor has unsaved edits. Unsaved runtime edits show a save bar (Discard, Save) at the bottom of the section.
- **Trips** is a work surface: title and count, the **Trip profile** and **Blocking scenario** menus, then View, Add trip, **Build trips…**, and Trip actions at the right.
- The **selection bar** shows above the table while Trips are selected: "N trips selected", **Shift…**, **Change pattern…**, **Regenerate…**, **Assign block…**, **Unassign…**, **Delete…**, **Clear**. **Change pattern…** with one Trip uses the single-Trip review (signed over the Trip, the target Pattern, and the target profile); with more than one it uses the batch dialog. While the page is scrolled far enough that the fixed duplicate heading row shows (Decision 0035), the selection bar is pinned above it in a compact form, so the commands stay in reach with the column names; the copy above the table keeps its space but is hidden, so exactly one copy is live. After a delete or a regeneration clears the selection, focus moves to Trip actions. Decision 0046 is unchanged apart from where Regenerate sits.
- The **Pattern** column shows a chip with the Pattern's short name (see "Short names"); the chip's tooltip is the full name. The **Block** column shows a pill with a dot in the Block's hashed colour and the Block label as text; its assignment menu is unchanged. The new-Trip row keeps its Pattern selector.
- **Headways (UR-8, HW-B and HW-X).** While **Show headways** is on, a bold **Departs** column (the Trip's first scheduled time) follows Pattern. The selection, Pattern, and Departs columns are pinned (`position: sticky`) in the table and at the same offsets in the fixed duplicate heading row; the last pinned column carries `trip-pinned-last` and a 1 px right shadow. A headway cell whose headway and the previous headway in the same column are both defined and differ carries `trip-headway-changed` (a warning-coloured inset left bar and fill). `markHeadwayChanges` in `src/application/tripsWorkspaceView.ts` decides it. Headways read with `formatDuration` (`:15`, `:07:30`). Headway calculation (Decision 0034) is unchanged.
- **Selecting trips (UR-9, SEL-1 and SEL-2).** The header checkbox still selects or clears all shown Trips. The caret button beside it ("Select trips by…") opens a menu: Select all (N), Select none, Invert selection; one item per Pattern with its count; Not assigned to a block (N), disabled without a Blocking scenario; Run times have changed (N). A choice replaces the selection; with Ctrl or ⌘ held it adds to it. Each Pattern chip is a menu button (Select all N on <pattern>, Add them to the selection, Remove them from the selection); Ctrl-click or ⌘-click on a chip adds that Pattern's Trips without opening the menu. Shift-click on row checkboxes keeps range selection. The pure helpers are in `src/application/tripSelection.ts` (`tripIdsMatching`, `invertSelection`, `combineSelection`). Every selection change goes through `requestShiftScopeChange`, so a staged Shift asks first. Menus that open from the pinned duplicate heading row use `MenuButton`'s `fixedMenu` placement so they are not clipped.

### Spreadsheet grids (UR-7, UR-7b)

- Spreadsheet grids use `useGridNavigation` (`src/ui/shared/useGridNavigation.ts`). The table has `role="grid"` and an `aria-label`; editable cells are `role="gridcell"` with a roving tabindex (one cell has `tabIndex=0`). At rest: arrows move; Home and End go to the row's first and last cell; Tab runs through the row's cells, then the row's enabled buttons (Duplicate, Remove, Order), then the first cell of the next row, and Shift+Tab is the reverse (UR-14), so Tab leaves the grid only after the last row; Enter or F2 edits with the text selected; a printable key edits starting with that character; Backspace or Delete edits empty; double-click edits. While editing: Enter and Shift+Enter commit and move down or up; Tab and Shift+Tab commit and move on in the same order; Escape cancels; blur commits, or cancels a refused entry. A refused entry keeps the cell in edit mode with `aria-invalid`, a danger outline, and the parser's message in a `role="status"` line under the grid. The caller's `onCommit` parses with the domain parsers; the hook never parses. Cells that differ from the saved record carry a `--color-warn-border` corner mark, and the save bar names the count. Applied to the Runtimes editor (From, To, segments), the Nodes table (Name, Short, Notes), and the Pattern points (Cumulative mi). A cell that holds a native select marks it `data-grid-control`: Tab at rest moves focus into the select, keys other than Tab stay with the select, and Tab leaves it for the next cell. Row buttons (Duplicate, Remove) stay ordinary buttons after the row's cells (the hook's `rowProps` on each row joins them to the Tab order above), and "+ Add time band" focuses the new band's first cell.

### Blocking tab layout (UR-6d, BL-A)

- The layout is a `.blocking-top` grid: Unassigned trips (34%, at least 420 px) beside Current block while there is something to assign, and a 46 px rail (button "Expand unassigned trips, N", badge green at 0, warning at N > 0) when the list is empty or the planner collapsed it with "Collapse unassigned trips" (stored as `{"collapsed":true}` under `transit-costing-tool.blocking-unassigned-collapsed.v1`; malformed reads as not collapsed). The change animates over 200 ms unless `prefers-reduced-motion`; below 1100 px the grid stacks. Focus moves between the panel and the rail when one replaces the other. The Minimum layover is unreachable while the list is empty (nothing to classify).
- Sortable column headings show ▲ or ▼ beside the label of the sorted column only. Other columns keep the space of a ↕ that shows on hover or keyboard focus, so labels do not move. The icon follows a left-aligned label and precedes a right-aligned (numeric) label. `aria-sort` and the button name state the order.
- Unassigned trips: each column heading has a sort button and a 24 px filter button in its top-right corner; the label uses the full width below it. "Compatible only" is a toggle button and "Clear filters" shows only while a filter is set; the Unassigned trip actions menu keeps only "Minimum layover…". Selected unassigned rows show a selection bar ("N selected", "Assign to Block <label>", Clear).
- Current block has a Block selector menu, "New block", and a "⋯" menu (Rename block…, Edit notes…, Delete block…). Selected block trips show a selection bar with "Remove from block…" and "Move to block…". "+ Add pull-out" and "+ Add pull-in" are table rows shown only while missing. Findings are InlineNotes.
- The day summary is a seven-cell stat strip above the Blocks table, whose footer reads "Total · N blocks".
- React presents application-service results without calculating ownership, compatibility, findings, or summaries.

## Phase 4 implemented Blocking conventions

- Blocking uses Trip Profile, Blocking Scenario, selected Route, and Day as context. The selected Route filters candidate Trips but never hides or truncates activities in the selected Block.
- Blocking Scenario is a named all-service-day arrangement. Its Profile relationship is immutable. Empty-create, duplicate, rename, and delete actions must state their complete scope.
- Trips adds a Blocking Scenario selector filtered to the selected Trip Profile. Its Block column is the assignment control of Decision 0025 (it was read-only under Decision 0021) and reflects only that selected arrangement. The selector is non-authoritative UI context and follows the Phase 3R menu, checked-item, focus-return, dismissal, wrapping, and responsive rules.
- Every Blocks table column is sortable. Selecting a Block in Current Block is activated only by clicking its name; the row may indicate the active Block but is not itself a control. The Blocks table footer shows aligned known subtotals for Revenue, Platform, Layover, Layover %, and Deadhead. Incomplete status exposes its findings on hover and keyboard focus. The Current Block selector highlights its selected menu item in blue, matching the Route Pattern selector.
- Assignment, atomic reassignment, removal, ordering, and activity editing must be completely keyboard operable. Drag-and-drop cannot be the only method.
- Operationally infeasible Blocks remain visible with planner-facing text and accessible status. Color is supplemental. Structural command rejection must identify the record and required correction.
- The selected Block always shows its complete ordered activity list, including every Route represented in imported multi-route data. Phase 4 prevents new cross-route assignment to non-empty Blocks.
- Block-level status and findings identify incomplete or infeasible work. The selected-day summary shows service quantities without separate complete/incomplete count tiles; valid but incomplete Blocks contribute known hours, and incomplete mileage is not displayed as zero.
- Dense Blocking tables retain compact controls, horizontal overflow, stable identifying columns, predictable focus after dialogs and writes, and usable desktop and narrow-width layouts.

## Phase 1 route definition

- Dense tables commit text and numeric edits on blur. This avoids local-save writes racing with active keyboard entry. Enter commits numeric values; Escape restores the saved value. Select changes and explicit actions commit immediately.
- Numeric fields retain their last saved value when blank or invalid input is left in the field, show an announced inline error, and treat zero as a valid value.
- Wide tables scroll horizontally on narrow screens. The left identifying column remains frozen on desktop table scroll.
- Removing a Node or a Pattern point is a draft change, not a modal confirmation. A removed Node row shows **Will be deleted** with **Undo**; the removal is applied by **Save nodes** or **Review and save** (Pattern), whose review states the effect on Patterns, Runtimes, Trips, and Blocks, and **Discard** restores the saved collection (see the Route conventions in this document, Decision 0014, and Decision 0041). The older modal confirmation for a single removal no longer exists.
- Pattern point order uses visible up and down controls. Repeated node selections are valid and are described in the empty state. Add-node and add-point actions appear after their respective lists, preserving an uninterrupted entry sequence.
- Validation is calculated by the domain layer, but message keys and rule identifiers are never shown to users. Findings are translated into concise planner-facing text. Route-level findings appear with the affected field. New blank node and pattern drafts use a required-field placeholder rather than immediate validation messages; validation remains available to later workflow checks.
- A primary tab whose prerequisite is missing is disabled with an explanatory title (Trips needs a Pattern with at least two points; Blocking needs a Route and a Trip Profile; Costing needs a Scenario). A disabled tab does not imply missing route data.
- New Project is the single, visually prominent project-creation action. The blank-project view provides only concise orientation text.
- Project, scenario, duplicate-scenario, and reverse-pattern names use compact in-app dialogs. Required-name feedback is visible, Enter submits, and Escape cancels. Dialogs without a visible field label retain a screen-reader label. Reverse creation collects a name and completes directly without a separate confirmation.
- Compact destructive actions in tables use a subtle trash icon with an accessible name and tooltip. The destructive confirmation continues to state the effect before the record is removed.
- The selected project, scenario, and route are stored as non-authoritative browser UI preferences. On startup, each identifier is checked against current local records and safely falls back when a saved selection no longer exists.

## Phase 2R safe route editing

- Nodes are edited as a local table draft. **Save nodes** (in the Nodes save bar) is the only write action. Pending deletion rows state **Will be deleted** and offer **Undo**; **Discard** returns the saved collection and moves the focus to **New node**.
- Patterns are edited one at a time as a local draft. A new, duplicated, or reverse Pattern is marked **Unsaved** and does not change Runtimes or Trips until **Review and save** succeeds. The Pattern save bar ("N unsaved changes in this pattern", or "New pattern — not saved") and its **Discard** and **Review and save** buttons appear only while the selected Pattern has unsaved edits. New Nodes are not available in a Pattern selector until their Node draft is saved.
- The **Add pattern** action is placed at the bottom of the Pattern list so the list reads top-to-bottom as existing Patterns followed by the creation action. **New node** and **Add pattern** are disabled while a Node or Pattern save is running, so a draft is never opened in the middle of a save whose reload follows.
- Changing the Route, project, scenario, primary tab, or adding a route while a Node or Pattern draft is dirty opens **Save route changes before leaving?** with **Save**, **Discard**, and **Cancel**. Save follows the ordinary impact review; Pattern work is resolved before Node work.
- Deterministic Pattern structure changes open a **Save and rebalance** decision. New inserted points receive their predecessor's scheduled time and a zero first segment; removing an intermediate point merges the adjacent runtime segments.
- A reordered or broadly replaced Pattern opens the destructive **Save and reset service** decision. It removes only profiles, assignments, trips, historical generation records, and revenue-trip block activities owned by that Pattern. Empty blocks remain.
- A timetable-order conflict appears above the Pattern save bar and names the conflicting Patterns and timepoints. It is not a global banner and cannot be overridden by deleting service.

## Phase 2 runtime editor

- The Trips tab becomes available after the selected route contains a pattern with at least two points. The page retains the existing project, scenario, and route context controls.
- The scope selectors in header row 2 always show Route. On Trips, they also show Day and Direction. The Route tab shows neither Day nor Direction because Pattern editing owns direction assignment. Blocking uses Trip Profile, Blocking Scenario, selected Route, and Day but not Direction. Runtime Pattern and both Profile controls belong to their respective workflow-section headers.
- Runtime bands are compact table rows. The left band-name column remains frozen; segment columns scroll horizontally as needed. Segment headers show the originating and destination node names rather than identifiers. Each row provides a calculated **Total** runtime after the final segment, followed by Duplicate and Remove actions. Total is the sum of the band’s segment durations and updates as valid segment edits are committed. Duplicate inserts a fresh unsaved row immediately below the source with the same timing values.
- Profile edits are local to the editor until the user selects **Save**. This permits an incomplete new row or temporarily invalid band boundary without persisting unusable data. **Discard** and **Save** are in the save bar at the bottom of the section, shown only while the editor is dirty. The domain validator supplies planner-facing findings at save time.
- Runtime time and duration fields use 24-plus `H:MM` input. Blur and Enter commit a valid value; Escape restores the previous value. A blank duration states that a runtime is required and that zero remains valid.
- New and copied profiles are explicitly named in a dialog. A copied profile is independent and is assigned to the current service day. Reverse-copy is offered only for a compatible reversed node sequence; it identifies the target pattern and states that segment runtimes will be reversed.
- No generated trips exist at this package. Band-boundary edits therefore do not claim a trip impact. The later trip-generation workflow will surface departures that fall into intentional runtime gaps.
- When there is no usable pattern, the Trips tab explains the prerequisite instead of exposing an incomplete editor.

## Shared workflow and table hierarchy

- A full-page planning workflow uses vertically stacked work surfaces (see "Surfaces and actions"). Each has one compact header for its title, supporting text, and actions. Do not add a second ordinary card inside a work surface solely to contain the controls or table.
- A dense table is a `data-grid` viewport: it has a neutral one-pixel frame, horizontal scrolling when required, and an 8px separation from the preceding content. The grid frame contains the table header and body; its grey header is not a competing section boundary.
- Notices, prerequisites, and destructive-impact messages use an accent treatment only when they communicate state. They are not substitutes for ordinary workflow sections or data-grid frames.
- Blocking: removing a Trip, Pull-out, or Pull-in from a Block asks first through the Confirm dialog and names the activity; deleting a Block or a Blocking Scenario shows what it removes (Trips, deadheads, and activities, or Blocks and activities, from `previewDeleteBlock` and `previewDeleteBlockingScenario`) and deletes with the reviewed source signature, closing the dialog if the source changed. A Trip from another Route shows that Route's short name before its Pattern name in the Pattern pill (`31B · Pattern`); a Trip of the selected Route shows the Pattern name alone. Pills carry the full name as a tooltip. Block hours and miles use the Costing rounding (two decimals, half away from zero). "Move Trip N" counts Trips only, and "No current issues." is a plain note, not a warning. Blocking loads apply only the latest response.
- Every modal dialog is built by `ModalDialog` (`src/ui/ModalDialog.tsx`), which follows the WAI-ARIA modal dialog pattern: focus moves to the control marked `autoFocus` or to the first focusable control; Tab and Shift+Tab stay inside, and focus that escapes is pulled back; Escape cancels unless the dialog is busy; on close, focus returns to the control that opened it (for a menu item, the menu's trigger). Each dialog has an accessible name (`labelledBy` the heading id, or `label`). A submitting dialog is a dialog section that holds a form. A menu item that opens a dialog never refocuses its trigger.
- Menus (`MenuButton`): a choice among alternatives is `menuitemradio`; an independent toggle (`kind: 'checkbox'`, the Display options) is `menuitemcheckbox`; Escape returns focus to the trigger at once; Tab closes an open menu and moves on. After an action removes or disables the control that was used (Shift drawer steps, Discard in the Runtime or Node editor), focus goes to the pressed control or to a neighbour in the same area, never to the page.
- Accessibility baseline checked by `tests/ui/keyboard.spec.ts` with axe-core: dialog names, labels, one `main` landmark, one `h1` per workspace (a visually hidden `h1` where the screen shows no visible one), `scope="col"` on table column headers, `aria-invalid` and `aria-describedby` on a field that shows an error, a labelled file input, colour contrast, and target size (see "Accessibility" under "Interface revision").
- Unsaved input is never dropped silently. A Runtime profile with unsaved edits asks Save, Discard, or Cancel before the Runtime Pattern or Profile, the service day, the Direction, or the tab changes, and the browser's leave prompt covers a reload. A staged Shift asks to be discarded before any of those changes and before a Runtime save, because a save reloads the Trips; with both open, the Runtime question comes first. An Add-trip row that has a Pattern or a first time entered asks Cancel or Discard before the service day, the Direction, the Trip Profile, or the tab changes (after the Runtime and staged-Shift questions, one question per press); an empty row is dropped without a question, and a Runtime save keeps the row. Build Trips closes without a prompt and keeps its values for the next time it is opened (a successful build clears them). Saving Nodes keeps an unsaved Pattern draft, and saving a Pattern keeps unsaved Node edits. Escape in a numeric or runtime time field restores the saved value and writes nothing.
- Stored selections (`localStorage`) are checked field by field: a value of the wrong shape reads as not stored. The Blocking Scenario chosen in Trips and in Blocking is remembered for each Trip Profile.
- Delete dialogs close when the deletion is refused (a stale review, Decision 0041) and show the refusal in the error banner; nothing is deleted, and a new review shows the current impact. This holds for Route, Scenario, Project, Pattern, Runtime profile, and Trips deletion. The Node save review also lists the pull-out, pull-in, and deadhead activities the save removes ("Removes 3 pull-out, pull-in, or deadhead activities in 2 Blocks."), and the Trip Profile delete confirmation says "Also deletes 2 Blocking Scenarios and their Blocks." ("1 Blocking Scenario and its Blocks" for one) when the profile owns any; both lines are absent at a count of 0.
- The Project menu shows the last backup time and, when the browser did not grant persistent storage (refused or unsupported), a second line under it: "This browser may clear local data. Export backups regularly." Nothing is added when storage was granted or the browser has not been asked yet (it is asked after the first successful save).
- Error text shown to a planner comes from the application's own wording through `userFacingError` (`src/ui/errorMessages.ts`); technical text from the browser, Dexie, or JavaScript, and raw message keys, are never shown. A failure message says what did not happen and what to do next. A read-only tab shows an information notice (`notice info`) and "Read-only" in the header; edit controls stay visible and writes are rejected.
- New UI elements must use the surface levels and these roles before introducing a new bordered box style. A different container treatment requires a functional reason, such as a modal decision, a nested list/detail editor, or a state-specific notice.
- Runtimes and Trips are work surfaces whose header holds their actions (UR-6c; see "Trips tab layout"). A profile menu lists saved profiles first, marks the selected profile, and separates lifecycle commands from selection. Runtime Pattern remains a native labeled selector because it is Pattern-owned. Runtime **Actions** groups the Route's calculation method (**Calculation method (whole route)**, changed through a confirmation that states the profiles and Trips affected; Decision 0045), CSV export, and service-day copy (**Copy runtimes from another day…**). **Add time band** is the last row of the runtime table. Runtime-profile CSV and Trips-table CSV exports stay in their owning workspace's **Actions > Data** group; neither has an import. Runtime profile export is unavailable while its editor has unsaved changes because export uses the saved profile.
- View menus for Runtime profile, Trip profile, and Blocking scenario use the same small bold field label; inside a work-surface header the label sits beside the selected value. Lifecycle commands such as New, Copy, Rename, and Delete remain quasi-button actions within the menu and are visually distinct from view selection.
- The Trips header holds **View** (checkbox items: Show runtime bands, Show headways, Round displayed times), **Add trip**, the primary **Build trips…**, and a ⋯ **Trip actions** menu. The menu holds only **Undo last regeneration (N trips)**, **Copy trips from another day…** (distinct from **Copy profile**), and **Export trips CSV**. Commands that act on selected Trips are buttons in the selection bar (see "Trips tab layout"), which keep the disabled rules and hints of the former menu items. **Regenerate…** is always present in the selection bar while Trips are selected and acts only on selected Trips with changed runtimes, so select-all is safe. **Undo last regeneration (N trips)** is a separate Trip actions item, listed only while the saved undo applies to the visible schedule, and never shown disabled for that reason (Decision 0046). The row trash icon and bulk **Delete…** use the same impact-aware deletion confirmation.
- Trips uses page-level vertical scrolling. When the schedule headings move above the viewport, a fixed duplicate heading row appears at the top and stays aligned with the table's measured column widths. Its horizontal scroll position follows the data grid, and no nested vertical scroll area is used.
- Build Trips opens a non-modal drawer docked to the right edge of the application, matching Shift Trips. It has Pattern, First Trip, Headway, Number of Trips, Last Trip, resolved runtime-profile context, Build, and Cancel. Number of Trips and Last Trip are mutually exclusive: entering either disables the other. Last Trip includes a departure that falls exactly on the headway sequence. A request is bounded to 500 Trips whichever of the two limits is used: Number of Trips may not exceed 500, and Last Trip may not produce more than 500 departures.
- When saved trips use earlier runtimes, a warning note "Run times have changed for N trips" with a **Select these trips** button stays visible immediately above the table; the button selects every shown Trip whose runtimes changed, which puts **Regenerate…** one click away. When the assigned Runtime profile cannot calculate one or more of the affected Trips, a plain status line (`role="status"`) directly under it gives their count and each distinct reason once, for example "2 Trips cannot be recalculated. No Runtime band covers its first departure. Add or extend a Runtime band." Nothing is shown when every affected Trip can be recalculated. A visible `Run times changed` note marks each affected row, and **Regenerate…** is enabled only when an affected row is selected.
- Shift is a mode of the Trips selection bar (UR-15; it replaced the compact panel docked to the lower right edge, U10). **Shift…** turns the bar into a toolbar named "Shift selected trips" that replaces the selection commands in the same place, so it stays beside the rows it moves, follows the bar when it is pinned above the fixed headings, and covers no row. The pinned compact copy keeps the step buttons, the net shift, **Discard**, and **Done**. The bar shows "Shift N trips", the net shift ("2 minutes later") as a status, two step buttons that name their size and direction ("← 5 min earlier", "5 min later →"), and a **Step** radio group of 1, 5, 10, and 15 minutes beside a **Step minutes** field for any other whole number of minutes; an invalid step disables both step buttons and says why. Each press creates a transient signed minute operation; Undo and Redo apply only to that drawer operation sequence. The table shows the staged times and text status before **Done** makes one atomic write. **Discard**, Close, or Escape write nothing. Route, Day, Direction, Trip Profile, tab, and selection changes request discard before changing scope. A stale preview requires discard and reopening Shift.
- Target-first copy dialogs keep the selected Day fixed, name the affected scope once, and require a preview before commit. Destructive empty-source Trip copies require an explicit clear-target acknowledgement and use the destructive confirm treatment.
- Batch actions retain checked rows on cancel and return focus to their trigger. A reviewed batch preview names every selected record as eligible or ineligible; confirmation is unavailable when any selected record is ineligible.

## Phase 2 trip building

- The Trips workspace is vertical: the runtime editor is first and the combined materialized schedule is last. This keeps the runtime prerequisite visible while making the generated schedule the working surface. (The generation-set editor that sat between them is gone: see the next bullet.)
- **Superseded by Decision 0010 and removed in review package X01:** the generation-set editor names and selects a saved set, then exposes pattern, first departure, headway, and one explicit generation limit. The end-time option is labeled **Inclusive end time** so a departure at that time is expected. Existing sets are loaded into the editor; choosing one prepares its next generation revision locally and does not write until confirmation.
- Generation and regeneration always open a preview dialog. The dialog summarizes additions, changes, removals, overridden shifts or pattern changes, and affected future block references before it offers a confirm action. Escape and Cancel close the dialog without a write.
- The combined schedule selects one service day and interlaces all trips in the selected direction. When patterns share a timetable column, rows sort by the earliest common timepoint; schedules without a common column fall back to initial departure. It uses fixed compact summary columns and reveals scheduled points through a per-trip detail row instead of creating unlimited timepoint columns. This keeps alternating, staggered, short, and full-length patterns visible in one table without doubling long schedules by default.
- Multi-trip selection uses visible checkboxes in the frozen first column. Shift-clicking a second checkbox selects the inclusive range between the last non-shift selection and that row, using the rows currently visible in the table; the header checkbox selects or clears all visible rows, and the "Select trips by…" menu beside it selects by Pattern or status (see "Trips tab layout"). A signed whole-minute shift is applied to all checked trips. Keyboard users can operate each native checkbox and retain table focus after the schedule reloads.
- Pattern changes are individual-trip actions. The user chooses a target pattern, then sees old and recalculated timepoints in a second preview before confirmation. The target pattern must have a runtime profile assigned for the current service day.
- Generated trips show **Generated**. Shifted and pattern-changed trips show an amber status marker with an explanatory label. The Block column is scoped to the selected Blocking Scenario. Its pill provides same-day Block choices and a confirmed unassign option; the selection bar's **Assign block…** and **Unassign…** do confirmed multi-Trip assignment and unassignment.

## Phase 4 manual blocking

- **Blocking** is a primary workspace after Route and Trips. Its scope selectors in header row 2 identify Trip Profile, Blocking Scenario, and service day. The selected Route filters only candidate Trips.
- The layout of **Unassigned trips** and **Current block** is BL-A (see "Blocking tab layout" under "Interface revision"). The Block selector lists Blocks for the selected day. The Block table always displays the complete ordered activity list, including imported activities outside the selected Route. The lower row shows Block status and a selected-day summary; its Trips count includes revenue Trips only.
- Empty Blocking Scenarios and empty Blocks are valid states with direct creation actions and explanatory empty-state text. Scenario and Block deletion use explicit confirmation dialogs that name their complete scope and consequences.
- Unassigned Trips offers a compatible-only filter for the Block's implicit appended revenue position. Its compact Pattern, Start, From Time, To Time, End, and Assign columns mirror the relevant Current Block fields. Assign buttons communicate compatible, deadhead-needed, conflict, and incomplete states.
- Unassigned Trips does not expose a placement selector; ordinary Assign adds a Trip at the end of current revenue work, before any pull-in. **Compatible only** is a toggle button and **Minimum layover…** is in the Unassigned trip actions menu. The minimum can be a fixed number of minutes per connection or a percentage of the preceding Trip's revenue runtime; it is a browser UI preference used to classify candidates and does not modify persisted Blocks. Current Block uses a leading multi-select checkbox column followed by #, Pattern, Start, From Time, To Time, End, Deadhead, Layover, and Actions. The # column numbers revenue Trips only. Its Deadhead cell presents a compact plus icon for each eligible connection, then a clickable saved duration. Pull-out and pull-in editing uses a relative whole-minute offset from the adjacent revenue Trip. The deadhead dialog can apply its values to matching consecutive From/To Node pairs in the current Block; Layover remains the separately derived remainder. Revenue Trips and boundary activities use the same circled-X removal icon; multi-Trip reassignment and removal are atomic commands in the block's selection bar.
- The Current Block selector orders Block labels by natural numeric/alphabetic order. Standalone deadhead activity rows are not repeated in the table; their values are represented on the preceding revenue-Trip row.
- Native buttons support assignment, reassignment, removal, ordering, activity editing, and destructive actions. Drag-and-drop is not required for any Phase 4 operation. Unassigned Trips and Current Block use the same inclusive shift-click range-selection behavior over their visible Trip rows. Selection-dependent actions appear in a selection bar while rows are selected.
- Multi-file CSV exports are delivered as one ZIP download containing the stable CSV files. A single export click must not initiate multiple independent downloads that desktop file associations may open in separate spreadsheet windows.
- Activity and summary findings use text status in addition to color. Finding links provide a keyboard-operable return path to the selected Block. Activity and schedule tables retain the `data-grid` frame and horizontal overflow on narrow layouts.
- Trips adds a labeled **Blocking scenario** menu immediately beside its **Trip profile** menu (the label was "Scenario" before review package U07, which the global Scenario selector also uses). It is filtered to that Trip Profile and scopes the Block assignment pill and bulk Actions. **No Blocking Scenario** appears only when no scenario exists or the selected scenario was removed. Changing this selector does not alter Trip editing scope.
- Block summaries report **Revenue** as Running Time plus usable Layover, while retaining **Running** as the sum of scheduled revenue-Trip durations. The selected-day stat strip shows service quantities without repeating complete/incomplete Block counts; each Block’s own status and findings remain in the Blocks table.
- All trip time fields, summaries, and previews use shared 24-plus service-time formatting. The schedule never converts after-midnight service to a wrapped clock time.
